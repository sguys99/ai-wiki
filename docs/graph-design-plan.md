# 그래프 페이지 재설계 계획

작성일 2026-11-16. 대상은 사이트의 `/graph/` 페이지다.

## 1. 배경과 목표

사이트에는 이미 `/graph/` 페이지가 있다 (Phase 5, 커밋 `760abdbb`). 캔버스 force 배치, 호버 이웃 강조, 카테고리 칩, 카테고리별 텍스트 목록을 갖췄다. 다만 121노드 시절에 만든 화면이라 지금 규모에서는 관계를 읽기 어렵다. 이번 작업은 **기존 `/graph/` 를 전면 재설계**한다 (2026-11-16 사용자 결정).

목표는 세 가지다.

- wiki 전체의 관계 구조가 한눈에 읽힌다 (어디가 뭉쳐 있고 무엇이 허브인지).
- 한 페이지에서 출발해 이웃을 따라가며 탐색할 수 있다.
- 사이트의 Constellation 디자인 언어 안에서 세련되게 보인다.

- 줌과 팬이 없다. 342개 노드가 고정 크기 캔버스 하나에 들어간다.
- 허브 하나가 엣지 118개를 가져 전체가 한 덩어리로 뭉친다.
- 색이 도메인 2가지뿐이라 카테고리 8개가 구분되지 않는다.
- 노드를 찾는 검색이 없다. 호버 외에는 제목을 볼 방법이 없다.
- 노드를 누르면 바로 페이지로 이동해, 그래프 안에서 이웃을 따라가는 탐색이 끊긴다.
- 특정 노드를 가리키는 공유 URL이 없다.

## 3. 유지할 제약

- 번들러 없음. 브라우저 스크립트는 `<script defer>` 로 싣는 vanilla JS다.
- 색은 CSS 토큰을 런타임에 읽는다. 라이트와 다크 테마 토글이 그대로 따라와야 한다.
- 스크립트가 실패해도 카테고리별 텍스트 목록으로 모든 페이지에 갈 수 있다 (접근성 판본).
- 홈 히어로 `constellation.js` 가 `graph-core.js` 와 `graph.json` 을 함께 쓴다. 깨뜨리지 않는다.
- `BASE=/ai-wiki` 배포 경로에서 동작한다. `npm run build:strict` 가 통과한다.
- 모바일 폭에서 가로 스크롤이 없고 터치로 조작된다.
- `prefers-reduced-motion` 에서는 애니메이션 없이 정지 배치를 보여 준다.

### 추천

관찰 결과는 사전 추천인 **A를 기본 화면으로, B를 선택 시 초점 모드로**를 지지한다. A는 조감을 가장 잘 해내지만 허브를 고르면 다발이 빽빽해지는데, 이 약점이 정확히 B가 잘하는 장면이다. 반대로 B는 시작 화면이 없다는 약점을 A가 메운다. B의 2-hop은 24 ~ 32개로 제한하고, 큰 허브에서는 라벨을 다 그리지 말고 상세 패널 목록에 맡긴다.

다른 시안에서는 값싼 것만 빌린다.

- C의 카테고리 간 링크 수: 섬 배치 없이 8 × 8 작은 행렬이나 범례 옆 표로 넣는다. 데이터를 세기만 하면 되고 라이브러리가 필요 없다. 다리를 누르면 연결 쌍을 보여 주는 동작도 행렬 칸 클릭으로 옮길 수 있다.
- D의 연도 배치: 기본 화면이 아니라 선택 노드의 이웃을 연도순으로 펼치는 "계보 렌즈"로만 둔다. D 패널의 "더 이른 해, 같은 해, 더 늦은 해" 이웃 목록은 그대로 A 패널에 옮길 만하다. 렌즈 자체는 Phase 5 뒤로 미뤄도 된다.
- E는 넣지 않는다. 남긴다면 별도 실험 페이지 정도이고, 본 페이지에 three.js를 들이지 않는다.

가져오지 않을 것은 C의 섬 배치와 묶음 엣지(d3 전체와 870줄 규모), D를 기본 화면으로 쓰는 것, E의 3D와 three.js, B의 제한 없는 2-hop 궤도와 수직 방사형 라벨이다.

비용은 d3-force 3.0.0과 그 의존 모듈(d3-dispatch, d3-quadtree, d3-timer)을 npm으로 받아 `static/` 에 두는 것, 그리고 A와 B 두 배치를 한 스크립트에서 전환하는 구현이다. B는 라이브러리가 없으므로 추가 의존은 d3-force 하나다. A는 지금 오프라인 대체가 없으므로 3절 제약대로 텍스트 목록 대체를 붙여야 한다.

**사용자가 정할 것**: 노드를 고르면 A 화면 위에서 이웃만 강조하는지(지금 A의 선택 화면), 아니면 B의 동심원 화면으로 전환하는지다. 전자는 구현이 작고 맥락이 남지만 허브에서 빽빽하다. 후자는 허브도 읽히지만 두 배치를 오가는 전환을 만들어야 한다.

### Phase 2 전에 답할 질문

1. 초점 모드는 A 위의 강조로 충분한가, B 동심원으로 전환해야 하는가 (위 결정과 같다).
2. C의 카테고리 간 링크 수 행렬과 D의 계보 렌즈를 Phase 4 본체에 넣는가, Phase 5 추가 기능으로 미루는가.
3. 모바일에서는 344노드 전체 조감으로 시작하는가, 검색과 B 궤도로 시작하는가. 실기기 핀치와 Safari 확인을 Phase 2 설계 전에 할지도 함께 정한다.

## 5. 함께 반영할 것 (요청에 없었지만 필요한 항목)

- `graph.json` 노드에 `year`, `type`, `tags` 추가. 필터, 시안 D, 상세 패널이 이 값을 쓴다.
- 노드 검색. 제목을 입력하면 해당 노드로 화면이 이동한다.
- 딥링크. `#node=category/stem` 으로 특정 노드를 선택한 상태를 공유한다.
- 클릭 동작 변경. 클릭은 선택과 패널 열기, 패널의 버튼이 페이지 이동을 맡는다.
- 카테고리 8색 구분. 도메인 2색 안에서 명도와 채도로 나누거나 범례를 둔다 (시안에서 결정).
- 키보드 조작. 방향키로 이웃 이동, Enter로 열기, Esc로 선택 해제.
- 제목 라벨 표시 규칙. 줌 수준과 degree에 따라 라벨을 드러낸다.

## 6. 추가 기능 (2026-11-16 사용자가 네 가지 모두 범위에 포함)

- **wiki 페이지마다 미니 이웃 그래프**: 각 문서 하단에 그 페이지의 1-hop 그래프를 넣는다. `graph.mjs` 주석에 이미 계획으로 적혀 있다.
- **학습 경로 겹쳐 보기**: overview의 `study_path` 를 그래프 위에 번호 붙은 경로로 표시한다.
- **약한 연결 리포트**: degree가 낮은 페이지 목록을 보여 wiki 보강 대상을 찾는다.
- **최근 추가 강조**: 최근 ingest한 노드를 표시해 지식이 어디서 자라는지 보여 준다.

그래프 페이지 본체(Phase 4)를 먼저 끝내고 Phase 5에서 하나씩 붙인다. 네 기능은 서로 독립이라 순서를 바꾸거나 중간에 멈출 수 있다. 상세 설계는 `docs/graph-spec/06-extra-features.md` 에 있다.

## 8. 필요한 도구

사용자가 따로 설치할 것은 없다. 아래는 이미 있는 것이다.

- 디자인 스킬: `frontend-design`, `design-taste-frontend` (설치됨).
- 화면 검증: `playwright` (시스템 Chrome 구동, `pyproject.toml` 에 있음).
