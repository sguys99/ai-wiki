## 3. 방법론 및 아키텍처 (Methodology and Architecture)

### 3.1 기존 도구의 한계와 여섯 가지 해결책 (~22:30-24:30)

발표자는 Graphify가 필요한 이유를 기존 도구 세 종류의 한계에서 끌어온다.

| 기존 도구 | 발표자가 지적한 한계 |
|---|---|
| grep, find | 문자열만 찾고 구조적 관계는 이해하지 못한다. 함수 호출 관계를 찾으려면 정규식이 복잡해지고 동적 호출과 간접 참조는 놓친다 |
| IDE의 정적 분석 | 단일 프로젝트 안에서는 동작하지만 다른 프로젝트나 문서 사이의 연결은 찾지 못한다 |
| 정적 분석 도구 일반 | 코드만 분석해 설계 문서나 논문의 의미적 연결을 놓친다. README나 아키텍처 문서에만 적힌 설계 의도가 누락된다 |

지식 그래프의 해결책 여섯 가지는 구조와 의미의 동시 분석, cross-file 관계 자동 발견, 인터랙티브 시각화, 자연어 질의, 영구 저장에 따른 재활용, 증분 업데이트다. 발표자는 슬라이드 비교표를 근거로 관계 인식, cross-file, 시각화, 영구 저장 네 항목에서 지식 그래프가 앞선다고 정리한다.

### 3.2 지식 그래프의 세 구성 요소 (~24:30-26:00)

| 구성 요소 | 정의 | 담기는 값 |
|---|---|---|
| 노드 | 엔티티 | 코드에서는 함수, 클래스, 모듈. 문서에서는 개념, 인물, 기술 용어. 고유 ID와 소스 파일 경로, 타입 정보를 함께 저장한다 |
| 엣지 | 노드 사이의 관계 | 함수 호출, 클래스 상속, 모듈 import, 개념 참조. 관계 종류와 신뢰도 점수가 붙는다 |
| 속성 | 메타데이터 | 소스 파일 경로, 라인 번호, 신뢰도 점수, 커뮤니티 ID |

예시 다이어그램은 `main.py`가 `utils.py`와 `models.py`를 import하고 이들이 config와 database에 의존하는 구조를 표현한다. 색상은 엔트리 포인트, 모듈, 인프라, API 외부 연동으로 구분한다.

### 3.3 9단계 파이프라인 (~26:00-27:30, 모듈별 상세 ~27:30-38:00)

| 단계 | 모듈 | 책임 |
|---|---|---|
| 1 | detect | 폴더 재귀 스캔, 카테고리 분류, 민감 파일 필터링, 대규모 코퍼스 경고 |
| 2 | extract | AST 구조 분석(Path A)과 LLM 의미 분석(Path B)을 병렬 수행 |
| 3 | cache | 추출 결과를 해시 기반으로 캐싱해 변경된 파일만 재처리 |
| 4 | build | 노드와 엣지를 NetworkX 그래프로 조립하고 Leiden으로 커뮤니티 감지 |
| 5 | analyze | God Node, Surprising Connections, Suggested Questions |
| 6 | visualize | 인터랙티브 HTML, SVG, GraphML, Neo4j 등으로 내보내기 |
| 7 | transcribe | 영상과 오디오를 텍스트로 변환 |
| 8 | query | BFS와 DFS 기반 순회로 자연어 질문에 답변 |
| 9 | report | `graph_understanding_report.md` 생성 |

아홉 단계 전체가 CLI 명령 하나로 자동 실행된다. detect의 지원 카테고리는 코드, 문서, 논문, 이미지, 영상, 오디오이고, TypeScript와 JavaScript와 Python과 Go를 포함해 20개 이상의 언어를 다룬다 (~28:00). detect가 만든 정보는 `graphify-out` 폴더에 JSON으로 저장되며, 코드 파일은 AST 경로로, 문서와 논문은 LLM 경로로 보내진다 (~28:30-29:00).

### 3.4 이중 경로 추출 (Dual-Path Extraction, ~29:00-32:00)

extract가 Graphify의 핵심 단계이고, 두 경로의 결과를 마지막에 하나의 그래프로 병합한다.

**Path A는 구조적 추출이다.** tree-sitter가 23개 언어를 파싱해 AST를 만들고, 함수와 클래스와 import를 노드로, 호출과 상속과 의존 관계를 엣지로 추출한다. 코드를 실행하는 방식이라 LLM이 필요 없고 비용이 들지 않으며 같은 코드는 항상 같은 결과를 낸다. 발표자는 이 결정성을 토큰 절감의 근거로 든다.

**Path B는 의미적 추출이다.** Claude, Antigravity, Codex 같은 모델로 개념과 엔티티를 인식하고, 인용과 참조 관계를 찾고, 설계 결정의 근거까지 추출한다. 이미지는 비전 기능으로 UI, 스크린샷, 차트, 다이어그램을 이해한다. 토큰은 이 경로에서 소모된다. 발표자는 코드만 봐서는 알 수 없는 "왜 이렇게 설계했는가"가 그래프에 포함된다는 점에서 설계 근거 추출을 특히 중요하게 본다.

발표자가 함께 강조하는 설계 선택은 임베딩을 쓰지 않는다는 것이다. LLM으로 임베딩을 만들어 그래프를 그리는 방식이 흔하지만 Graphify는 NetworkX로 그래프를 그리며, 임베딩 모델을 거치지 않고 실제 텍스트 내용을 분석한다 (~05:00). 코드를 통해 분석하므로 환각이 줄고 토큰 사용량도 크게 절감된다는 것이 발표자의 설명이다 (~09:00).

### 3.5 신뢰도 태깅 (Confidence Tagging, ~35:30-36:00)

병합된 그래프의 각 엣지에 신뢰도 태그가 붙어 어떤 관계가 확실하고 어떤 관계가 추론된 것인지 드러난다. 발표자는 이 투명성이 Graphify를 연구 목적으로도 쓸 수 있게 한다고 평가한다 (~32:00).

| 태그 | 의미 | 점수 |
|---|---|---|
| `extracted` | 소스에서 직접 확인된 관계 | 1.0 |
| `inferred` | 합리적인 추론 | 0.6 ~ 0.9 |
| `ambiguous` | 불확실해 검토가 필요한 약한 추론 | 0.1 ~ 0.3 |

매 실행 후 자동으로 출력되는 항목은 God Node, 의외의 연결, 추천 질문, 신뢰도 점수, 구조적 연결이 없는 의미적 유사성 엣지, 하이퍼 엣지, 토큰 벤치마크다 (~16:00-16:30).

### 3.6 캐시와 빌드 (~32:00-34:00)

cache는 이미 추출된 파일의 결과를 저장하고 파일 해시로 변경 여부를 판단해 바뀌지 않은 파일을 건너뛴다. `--update` 플래그를 쓰면 변경된 파일만 재추출한다.

build는 프래그먼트를 통합 그래프로 조립한다. 순서는 AST 결과와 의미 결과 병합, 중복 노드 제거, NetworkX 그래프 객체 생성, Leiden 커뮤니티 감지다.

### 3.7 analyze의 세 가지 분석 (~34:00-35:30)

- **God Node**: 가장 많이 연결된 허브 노드를 찾는다. 새 프로젝트 합류 시 여기부터 읽으면 전체 아키텍처를 빠르게 파악할 수 있다는 것이 쓸모다.
- **Surprising Connections**: 직접 import나 호출이 없는데도 간접 연결된 모듈을 찾아 숨겨진 의존성과 암묵적 결합을 드러낸다. 코드 리뷰와 리팩터링에 유용하다.
- **Suggested Questions**: 그래프 구조를 분석해 탐색할 질문을 자동 생성한다. extract와 build 사이의 데이터 흐름을 묻는 질문이 예시다.

### 3.8 visualize, transcribe, query (~36:00-38:00)

| 출력 | 용도 |
|---|---|
| `graph.html` | vis.js 기반 인터랙티브 시각화. 노드 클릭으로 상세 정보를 보고 검색과 커뮤니티별 필터링을 지원한다 |
| SVG | 정적 다이어그램. 문서나 프레젠테이션 삽입용 |
| GraphML | Gephi나 yEd 같은 전문 도구에서 고급 레이아웃 적용 |
| Neo4j Cypher | 그래프 데이터베이스로 직접 import |
| Obsidian vault | Obsidian 노트 형태 출력 |
| wiki | 에이전트가 크롤할 수 있는 위키 생성 (~43:30) |

transcribe는 오디오와 비디오를 OpenAI Whisper로 텍스트 변환하며, 도메인 힌트로 전문 용어 인식 정확도를 높인다. 머신러닝 영상이면 Transformer와 attention 같은 키워드를 힌트로 준다.

query는 BFS로 광범위한 맥락을, DFS로 특정 경로를 깊게 추적한다. 토큰 예산을 설정해 응답 길이를 제한할 수 있다. 최종 결과물은 질의 가능한 `graph.json`, 인터랙티브 시각화 `graph.html`, 인사이트를 담은 리포트 마크다운 파일 셋이다.

### 3.9 AST와 tree-sitter (~45:00-50:00)

AST는 소스 코드의 구조를 트리 형태로 표현한 자료 구조다. 괄호, 세미콜론, 공백 같은 구문 장식은 버리고 함수 정의, 변수 선언, 조건문 같은 의미 단위만 남긴다. 루트는 보통 모듈이나 프로그램이고, 그 아래에 함수 정의, 클래스, 선언, 표현식이 자식 노드로 배치된다. 발표자는 `a`와 `b`를 더해 반환하는 함수를 예로 들어, 콜론과 들여쓰기와 공백은 사라져도 코드의 의미는 완전히 보존된다는 점을 보인다.

AST가 중요한 이유는 두 가지다. 언어 독립적인 코드 분석이 가능하다는 것과, 정규식이나 텍스트 매칭과 달리 코드 구조를 정확히 반영한다는 것이다. 컴파일러, 린터, IDE 코드 분석 도구의 기반 기술이며 확률적 모델이 아닌 결정적 방법을 쓴다.

Python은 표준 라이브러리 `ast`로 이 변환을 수행한다. `ast.parse()`가 AST 객체를 반환하고, `ast.dump()`로 트리를 텍스트 출력하며, `ast.walk()`로 모든 노드를 순회한다. Graphify가 tree-sitter를 쓰는 이유는 Python `ast`가 Python만 지원하기 때문이다.

| 비교 항목 | Python 내장 `ast` | tree-sitter |
|---|---|---|
| 지원 언어 | Python만 | 23개 이상, 동일한 API |
| 속도 | 느리며 대용량 파일에서 차이가 크다 | C 구현이라 수만 줄도 밀리초 단위 |
| 증분 파싱 | 없음 | 변경분만 log n 시간에 재파싱 |
| 오류 복구 | 불가능 | 문법 오류가 있는 코드도 부분 파싱 |

주요 지원 언어로 Python, JavaScript, TypeScript, Go, Rust, Java, C++를 든다. 다중 언어 프로젝트도 하나의 그래프로 통합할 수 있다.

### 3.10 노드와 엣지 추출 규칙 (~50:00-53:00)

AST에서 그래프를 만드는 하위 파이프라인은 여섯 단계다. 코드 파일이 tree-sitter로 파싱되어 AST가 생성되고, 여기서 노드와 엣지가 추출되어 그래프 프래그먼트가 나온다.

노드 ID는 파일명과 엔티티명을 언더스코어로 조합한다. `detect.py`의 `scan_folder` 함수는 `detect_scan_folder`가 된다. 함수 정의 노드에서는 함수 이름, 파라미터, 반환 타입을, 클래스 정의 노드에서는 클래스 이름, 부모 클래스, 메서드 목록을 추출해 노드 속성으로 저장한다. 호출 노드는 노드가 아니라 엣지로 변환된다.

| 엣지 유형 | 생성 조건 | 의미 |
|---|---|---|
| `call` | 호출 노드 발견 | 호출하는 함수에서 호출되는 함수로 |
| `import` | import나 from import 노드 발견 | 현재 모듈에서 가져오는 모듈로. 모듈 간 의존성 그래프의 기초 |
| `inherit` | 클래스 정의의 부모 클래스 속성 확인 | 자식에서 부모로. 다중 상속이면 여러 개 |
| `use` | 변수 사용, 상수 참조, 설정값 읽기 | 가장 일반적인 참조 |

실전 예시는 pandas를 import해 DataFrame을 가져오고 함수를 정의해 반환하는 코드다. 노드로 process와 DataFrame과 pandas가, 엣지로 process가 pandas를 import하는 관계가 나온다.

### 3.11 Leiden 커뮤니티 감지 (~53:00-54:30)

Leiden은 2019년 발표된 커뮤니티 감지 알고리즘으로 Louvain의 개선판이다. modularity를 최적화하면서 Louvain의 알려진 문제인 연결이 끊긴 커뮤니티 발생을 해결했다. resolution 파라미터로 클러스터 크기를 조절한다.

커뮤니티의 쓸모는 세 가지다. 모듈 구조를 자동 발견해 아키텍처를 이해하는 것, 관심사 분리를 검증해 설계 품질을 평가하는 것, 코드 변경 시 같은 커뮤니티의 다른 노드가 받을 영향을 분석하는 것이다.

### 3.12 핵심 라이브러리 (~54:30-55:30)

| 라이브러리 | 담당 |
|---|---|
| tree-sitter | 코드 파싱과 AST 생성 |
| NetworkX | 그래프 생성과 분석. 노드와 엣지 추가, 최단 경로, 중심성 계산, 직렬화를 제공하는 Python 대표 그래프 라이브러리 |
| Leiden 알고리즘 Python 구현체 | python-igraph 기반이며 `find_partition`으로 최적 커뮤니티 분할을 찾는다 |
| Python `ast` | 표준 라이브러리라 별도 설치가 필요 없다. tree-sitter가 모든 언어를 파싱하고 `ast`는 Python 코드에 한해 고수준 정보를 더하는 보완 역할이다 |

### 3.13 코드 워크스루 (~55:30-59:00)

발표자는 Graphify의 세 모듈을 실제 코드로 훑는다.

| 파일 | 함수 | 하는 일 |
|---|---|---|
| `extract.py` | `collect_files` | 소스 경로를 받아 코드 파일 목록을 반환 |
| `extract.py` | `extract` | 파일 목록을 tree-sitter로 파싱해 노드와 엣지를 추출 |
| `build.py` | `build_from_json` | 추출 결과 딕셔너리로 NetworkX 그래프 생성. 중복 노드는 ID 기반 자동 병합 |
| `build.py` | `cluster` | 그래프를 igraph로 변환해 Leiden으로 커뮤니티 감지 |
| `analyze.py` | God Node | 차수가 가장 높은 상위 n개 노드 |
| `analyze.py` | Surprising Connections | 다른 커뮤니티에 속하면서 연결된 노드 쌍 |
| `analyze.py` | Suggested Questions | 그래프 구조와 커뮤니티 라벨 기반 탐색 질문 생성 |

`extract`의 반환값은 노드 리스트, 엣지 리스트, 입력 토큰, 출력 토큰을 담은 딕셔너리다. AST 추출은 로컬 수행이라 토큰 사용량이 항상 0이다. 노드는 ID, 라벨, 파일 타입, 소스 파일 경로를, 엣지는 시작과 도착 노드 ID, 관계 유형, 신뢰도를 가진다. 직접 추출이므로 신뢰도는 항상 `extracted`이고 점수는 1이다. `cluster`는 각 노드 ID가 속한 커뮤니티 번호를 담은 딕셔너리를 돌려주며, 이 값이 노드 속성으로 저장되어 시각화 시 색 구분에 쓰인다.

전체 구현 흐름은 detect, extract, `build_from_json`, `cluster`, God Node, HTML 렌더 여섯 함수 호출로 이어지며 각 함수의 출력이 다음 함수의 입력이 된다.

### 3.14 CLI와 슬래시 스킬 (~42:30-43:30, ~14:30-15:30)

설치는 Claude Code나 Antigravity 화면에서 Graphify의 홈페이지 주소나 git 저장소 주소를 주고 스킬로 설치해 달라고 요청하면 끝난다 (~00:30-01:00, ~07:30). 이후 `/graphify` 슬래시 명령으로 전체 파이프라인을 실행하며 별도 설정은 필요 없다. 실행하면 폴더 안의 코드, 노트, 논문, 이미지, 텍스트, 영상을 정리해 `graphify-out` 폴더에 HTML, 마크다운, JSON, 캐시를 생성하고, 문서가 갱신되면 캐시를 참조해 변경분만 반영한다.

| 명령 | 동작 |
|---|---|
| `graphify` | 현재 디렉터리를 분석한다 |
| `graphify <경로>` | 지정한 경로를 분석한다 |
| `graphify ./raw` | Karpathy가 모든 자료를 raw 폴더에 넣고 분석한 방식을 그대로 옮긴 예시다 |
| `--update` | 캐시를 참조해 변경된 파일만 재추출한다 |
| `graphify path A B` | 두 개념 사이의 경로를 탐색한다 |
| `graphify explain` | 특정 노드에 대한 설명을 생성한다 |
| `graphify watch` | 파일 변경 시 그래프를 자동 동기화한다 |
| `graphify wiki` | 전체 폴더에 대한 위키를 빌드한다 |

논문이나 트윗은 URL만 넣으면 폴더로 옮기는 과정 없이 그래프에 바로 추가된다 (~14:30).

### 3.15 보안과 프라이버시 4계층 (~41:30-42:30)

| 계층 | 내용 |
|---|---|
| 민감 파일 자동 필터링 | `.env`, `.pem`, credentials 파일, AWS 키 파일이 detect 단계에서 제외되어 시크릿이 LLM에 전송되는 것을 원천 차단한다 |
| 로컬 처리 우선 | AST 추출은 100% 로컬 수행이다. tree-sitter가 로컬 머신에서 동작해 코드가 외부로 나가지 않고, LLM 의미 추출 결과도 로컬에 저장된다 |
| 완전한 감사 추적 | 모든 엣지의 신뢰도 라벨과 소스 파일이 기록되어 관계의 출처를 항상 추적할 수 있다 |
| 대규모 코퍼스 경고 | 파일 200개 이상은 의도적 선택을 요구한다. 자동으로 전체를 처리하지 않고 사용자 확인을 받는다 |

detect의 임계값은 파일 200개 또는 단어 200만 개이며, 초과 시 경고를 표시하고 하위 폴더 선택을 안내한다 (~28:30).

## 4. 주요 결과와 벤치마크 (Key Results and Benchmarks)

### 4.1 legalize-kr 시연 흐름 (~03:30-14:00)

발표자는 legalize-kr 저장소를 클론한 뒤 `graphify .`를 실행했다. 전체 법령이 너무 방대해 Graphify가 특정 폴더만 분석하라고 제안했고, 발표자는 특허법을 선택했다. 이후 흐름은 다음과 같다.

1. 코퍼스 규모를 파악하고 AST를 생성한 뒤 단계별로 실행하며 HTML 시각화를 만든다.
2. God Node를 찾고, Surprising Connections로 연결 경로를 찾고, Suggested Questions로 질문을 제안한다.
3. `graphify query`로 "특허 출원과 등록의 차이"를 묻는다. BFS와 DFS로 법령을 탐색해 답을 만든다.
4. Graphify가 deep 모드 재실행 시 등록, 심사, 거절 노드가 풍부해질 수 있다고 제안했고 발표자가 수락했다. 이 과정에서 API 오류가 나 다시 시도했다 (~11:00).
5. 산출물로 그래프 HTML, JSON, 마크다운 파일이 나오고, 출원과 등록의 차이는 표로도 정리되었다.

시각화 화면에서 "파리"를 검색해 파리 협약 관련 노드를 확인하는 장면도 나온다 (~05:30-06:00). 발표자는 이 그래프가 사람에게는 방대한 법령의 지도이고 LLM에게는 문서를 전부 열지 않고도 답을 찾게 해 주는 지도라고 설명한다.

### 4.2 토큰 절감 (~13:00-13:30, ~19:30)

이 영상의 핵심 주장이므로 측정 조건을 명시한다.

| 항목 | 값 | 출처와 조건 |
|---|---|---|
| 공식 벤치마크 | 71.5배 | Graphify 문서의 벤치마크를 인용했다. 측정 조건은 영상에 없다 |
| 시연 실측 | 657배 | legalize-kr 특허법 폴더에 "특허 출원과 등록의 차이"를 질의한 뒤 도구에 토큰 개선 여부를 되물어 받은 답이다 |
| 비교 대상 | 파일 전체 읽기 | 20만 토큰에 가까운 값 |
| Graphify 사용 시 | 292 토큰 | 그래프를 BFS와 DFS로 탐색한 경우 |

같은 답변에서 발표자가 함께 짚은 조건은 초기 투자 비용이다. 그래프와 JSON과 HTML과 마크다운 파일을 처음 만들 때 토큰이 들어가고, 657배는 그 이후 쿼리 시점의 값이다.

657배는 도구 자신이 산출한 값이지 외부 계측값이 아니다. 산술적으로도 292 토큰의 657배는 191,844 토큰이므로 비교 기준은 20만이 아니라 19만 대의 어떤 값이다.

### 4.3 처리 속도 (~40:30-41:00)

| 코퍼스 규모 | 처리 시간 |
|---|---|
| 50개 파일 (소규모 프로젝트) | 1분 이내 |
| 200개 파일 | 5분 이내 |
| 1,000개 파일 (대규모) | 약 8분 |
| 증분 업데이트 | 약 1분 |

10만 줄 규모의 코드도 약 8분이면 처리된다. 캐시 히트율은 80% 이상이고, 증분 업데이트를 쓰면 첫 실행 대비 5배 이상 빨라진다.

성능을 가능하게 하는 전략으로 발표자가 이름을 붙여 설명한 것은 두 가지다. 캐싱은 이미 처리한 파일을 다시 처리하지 않고 파일 해시를 기준으로 변경 여부를 판단한다. 청킹은 파일을 청크로 나누어 처리하되 같은 디렉터리의 파일은 같은 청크에 넣어 cross-file 관계의 추출 확률을 높인다.

### 4.4 Graphify 자체 분석 결과 (~33:00-34:00, ~53:30-54:00, ~59:00-59:30)

발표자가 Graphify로 Graphify 프로젝트 자체를 분석한 결과다. 영상에서 세 번 반복해 제시된다.

| 지표 | 값 |
|---|---|
| 노드 | 1,394개 |
| 엣지 | 2,141개 |
| 커뮤니티 | 63개 (Leiden) |
| 응집도(modularity) | 0.78 |
| Python 파일 | 20개 |

응집도는 1에 가까울수록 커뮤니티 내부 연결이 밀접하다는 의미이고, 발표자는 0.78을 매우 높은 수준으로 평가한다. 클러스터링 시각화에서는 extract 모듈, build 모듈, analyze 모듈이 각각 커뮤니티를 형성한다.

God Node 1위는 `extract.py`로 함수 48개와 관계 239개를 가진 핵심 허브다 (~34:00). 발표자는 프로젝트를 처음 접하는 개발자라면 이 파일부터 읽으면 전체 구조를 빠르게 이해할 수 있다는 의미로 해석한다.

### 4.5 네 가지 실전 사례 (~38:00-40:00)

| 사례 | 내용 |
|---|---|
| 코드베이스 학습 | 코드를 읽기 전에 그래프를 먼저 만든다. God Node로 핵심 모듈을 파악하고 연결로 아키텍처의 숨은 의도를 이해해 온보딩 시간을 단축한다 |
| 기술 부채 분석 | 과도하게 연결된 노드는 기술 부채의 징후일 수 있다. 분리 가능한 모듈로 리팩터링 우선순위를 정하고 커뮤니티 분석으로 관심사 분리를 검증한다 |
| 연구 코퍼스 관리 | 논문과 구현 코드를 함께 분석해 이론과 구현의 연결을 본다. 인용 관계와 개념이 한 그래프에 통합되어 분야의 지형도를 얻는다 |
| 개인 raw 폴더 관리 | Karpathy의 raw 폴더 워크플로를 그대로 따른다. 트윗, 메모, 스크린샷을 폴더에 놓고 그래프를 만들면 언제든 질의할 수 있는 지식 저장소가 된다. 예상하지 못한 연결의 발견이 가장 큰 장점이다 |

발표자는 영상 끝에서 Graphify의 핵심을 이중 경로 추출, 자동 클러스터링, 투명한 감사 추적 세 가지로 정리한다 (~01:00:00).

## 5. 한계와 향후 과제 (Limitations and Future Work)

영상에 별도의 한계 절은 없다. 발표자가 지나가며 짚은 트레이드오프와 이 자료 자체의 제약을 정리한다.

- **초기 구축 비용**. 토큰 절감은 쿼리 시점의 효과이고, 그래프를 처음 만들 때 Path B의 의미 추출에 LLM 토큰이 들어간다 (~13:00). 캐시와 증분 업데이트가 이후 비용을 낮춘다.
- **대규모 코퍼스 가드레일**. 파일 200개 또는 단어 200만 개를 넘으면 사용자 확인을 요구한다. 안전장치이면서 큰 저장소를 한 번에 그래프로 만들기는 어렵다는 뜻이다 (~28:30, ~42:30).
- **외부 LLM 의존**. 시연 도중 API 오류가 발생해 재시도했다 (~11:00). Path B는 네트워크와 quota 상태에 노출된다.
- **수치의 출처 한계**. 657배는 도구가 스스로 산출한 값이고 71.5배는 Graphify 문서의 값이다. 영상 안에서 독립적으로 계측한 절차는 없다.
- **자료 내부의 수치 불일치**. 지원 언어 수가 도입부와 detect 절에서는 20개 이상, extract와 tree-sitter 절에서는 23개 이상으로 갈린다. 처리 속도도 요약 문장은 파일 1,000개를 5분이라 하지만 바로 뒤 표는 200개가 5분 이내, 1,000개가 8분이다.
- **자막 노이즈**. 자동 자막이 고유명사와 숫자를 잘못 합성한다. God Node를 "간드", Louvain을 "루베인", vis.js를 "bj.js", `.env`를 "DMV", 엣지 2,141개를 "2114, 141"로 옮긴 사례가 있다. 정확한 인용에는 원본 슬라이드 확인이 필요하다.
- 향후 과제는 명시되지 않는다. 영상은 시청자에게 도움이 되기를 바란다는 인사로 끝난다 (~01:01:30).

## 7. 용어집 (Glossary)

| 용어 | 설명 |
|---|---|
| LLM Wiki | Karpathy가 X에 제안한 워크플로. 자료를 raw 폴더에 모으고 요약과 개념 분류를 거쳐 마크다운이나 위키나 그래프로 만든다 |
| Graphify | 임의 폴더를 하나의 NetworkX 그래프로 만드는 도구. `/graphify` 슬래시 스킬로 호출한다 |
| AST | Abstract Syntax Tree. 구문 장식을 버리고 함수 정의와 변수 선언 같은 의미 단위만 남긴 트리. 컴파일러와 린터의 기반 기술이다 |
| tree-sitter | C로 구현된 다언어 파서. 23개 이상 언어를 같은 API로 지원하며 증분 파싱과 오류 복구를 제공하는 Path A의 엔진 |
| NetworkX | Python 그래프 라이브러리. 노드와 엣지 추가, 최단 경로, 중심성, 직렬화를 제공한다 |
| Leiden | 2019년 발표된 커뮤니티 감지 알고리즘. Louvain의 개선판으로 연결이 끊긴 커뮤니티 문제를 해결했고 resolution으로 클러스터 크기를 조절한다 |
| Louvain | 커뮤니티 감지의 고전 알고리즘. Leiden이 보완 대상으로 삼는다 |
| modularity | 커뮤니티 내부 결합 강도 지표. 1에 가까울수록 강하다. 영상 사례는 0.78 |
| God Node | 차수가 가장 높은 허브 노드. 새 코드베이스 온보딩의 시작점 |
| Surprising Connection | 다른 커뮤니티에 속하면서 연결된 노드 쌍. 숨겨진 의존성과 암묵적 결합을 드러낸다 |
| Suggested Question | 그래프 구조와 커뮤니티 라벨로 자동 생성된 탐색 질문 |
| 신뢰도 태그 | 엣지 라벨. `extracted`(1.0), `inferred`(0.6~0.9), `ambiguous`(0.1~0.3) 세 가지로 감사 추적의 단위다 |
| 이중 경로 추출 | 결정적 AST 경로와 LLM 의미 경로를 병렬로 실행해 한 그래프로 병합하는 핵심 설계 |
| Whisper | OpenAI 음성 인식 모델. transcribe 단계에서 쓴다 |
| BFS / DFS | 너비 우선 탐색과 깊이 우선 탐색. query 단계에서 토큰 예산과 결합된다 |
| legalize-kr | 박정환이 만든 git 기반 대한민국 법령과 판례 저장소. 이 영상의 시연 데이터셋 |
