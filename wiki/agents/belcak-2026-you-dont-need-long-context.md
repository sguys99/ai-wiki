## 요약

에이전트가 버그를 고치는 동안 터미널에는 같은 오류가 수십 번 찍힐 수 있다. 이 출력을 다음 대화에 그대로 붙일 때마다 입력이 길어진다. Belcak 등의 실험에서 에이전트는 수정한 파일, 실패한 검사, 다음에 확인할 일을 메모한 뒤 새 대화에서 작업을 이어 갔다. SWE-bench Verified의 500개 문제에서 Claude Opus 4.5는 이력을 모두 읽을 때 70.0%를 해결했다. 대화가 1만 8천 토큰에 이르면 메모를 남기는 설정에서는 74.8%를 해결했다.

긴 문서에서는 모델이 필요한 대목을 파일에서 찾아 읽었다. 약 100만 자짜리 문법서에서 문장 하나를 번역하는 문제라면, 문장에 나오는 동사를 파일에서 찾아 용례가 있는 대목을 펼칠 수 있다. 원본은 계속 열어 볼 수 있고, 문서 내용 중에서는 검색 결과와 펼쳐 본 구절만 모델 입력에 들어간다. **작업이 길어도, 다음 판단에 필요한 정보는 한 번의 짧은 입력에 들어갈 수 있다.** 얼마나 짧게 줄여도 되는지는 과제와 모델에 따라 달랐다.

## 컨텍스트가 길어지는 두 가지 이유

컨텍스트는 모델이 이번 호출에서 볼 수 있는 토큰이다. 코드 수정 에이전트라면 사용자의 요청, 이전에 내린 명령, 프로그램 출력이 여기에 들어간다. 모델을 다시 호출할 때 이전 메시지를 모두 붙이면, 초반에 한 번만 필요했던 디렉터리 목록도 마지막 테스트를 실행할 때까지 입력에 남는다. context window는 모델이 한 번에 처리할 수 있는 토큰 수의 한도다. 입력과 새로 생성할 토큰을 이 한도 안에 담아야 한다.

논문은 오래 걸리는 과제와 입력이 긴 과제를 따로 측정했다. 차이는 긴 텍스트가 어디서 생기느냐에 있다.

| 구분 | 길이가 늘어나는 이유 | 논문에서 바꾼 조건 |
|---|---|---|
| 여러 단계가 필요한 과제 | 파일을 열고 고치고 검사할 때마다 실행 이력이 늘어난다. | 완료한 작업의 이력을 어느 시점에 메모로 바꿀지 정한다. |
| 처음부터 입력이 긴 과제 | 첫 질문에 딸린 문서만으로도 context window를 채울 수 있다. | 자료를 파일로 두고 모델이 근거를 찾아서 읽게 한다. |

두 번째 조건에서는 긴 문서를 다루는 문제가 여러 단계에 걸쳐 정보를 찾는 문제로 바뀐다. 검색어가 빗나가면 다른 표현을 써 보거나 앞뒤 문단을 더 읽어야 한다. 첫 호출의 입력은 짧아도 과제가 끝날 때까지 여러 차례 모델을 호출할 수 있다. 여기서 ‘짧다’는 보통 1만 6천~5만 토큰 규모라는 뜻이다. 연구진은 이를 당시 여러 모델이 지원하던 25만 6천 토큰 이상의 창과 비교했다(2.1절).

## 대화를 이어 가는 세 방식

코드 수정 실험에서 모델은 Bash 명령을 한 번 실행하고 결과를 받은 뒤 다음 행동을 정한다. 이때 모델이 파일에 적용한 수정은 디스크에 남는다. 새 대화에서 모델은 무엇을 수정했는지 메모나 파일을 읽어 확인할 수 있다. 연구진은 같은 실행 환경에서 대화를 구성하는 방식만 바꿨다. compaction은 이전 작업에서 다시 필요할 내용을 모델이 짧게 기록한 다음 새 대화로 넘기는 절차다.

| 방식 | 새 대화를 여는 시점 | 다음 판단의 근거 |
|---|---|---|
| 전체 이력 유지(FHA) | 과제가 끝날 때까지 같은 대화를 쓴다. | 처음 요청부터 직전 실행 결과까지 모두 읽는다. |
| 임계값에서 정리(EoCC) | 대화가 미리 정한 길이에 이르면 인계 메모를 작성한다. | 원래 요청과 메모에서 출발해 이후 실행 결과를 다시 쌓는다. |
| 행동마다 정리(SAC) | 행동 한 번을 마치고 그 결과까지 메모에 반영하면 새 대화를 연다. | 직전까지의 상태를 설명하는 메모와 원래 요청을 읽는다. |

![[assets/belcak-2026-you-dont-need-long-context/fig03.png]]

### 메모를 쓸 자리

논문의 표에는 ‘16K / 12K’처럼 숫자가 두 개씩 나온다. 앞의 1만 6천은 입력과 출력을 포함한 전체 상한이고, 뒤의 1만 2천은 메모를 쓰기 시작하는 임계값이다. 둘 사이에 여유를 두어야 모델이 기존 대화를 보면서 메모를 끝까지 작성할 수 있다. 전체 상한에 먼저 도달하면 해당 대화를 종료한다. 1만 2천 토큰을 정기적으로 지운다는 뜻으로 읽으면 표를 잘못 해석하게 된다.

메모를 읽고 작업을 이어갈 모델에는 어느 파일을 고쳤고 무엇을 확인해야 하는지가 중요하다. 예를 들어 ‘오류를 조사했다’만 남겨 두면 모델은 새 대화에서 어느 파일을 고쳤고 어떤 테스트가 아직 실패하는지 다시 찾아야 한다. 부록 G의 코드 작업용 프롬프트는 관찰한 사실과 아직 확인하지 않은 추측을 구분하고, 다음과 같은 내용을 남기도록 한다.

- 원래 요청과 완료 조건을 적는다. 요청 속에서 꼭 지켜야 하는 제약도 함께 넘긴다.
- 바뀐 파일, 관련 심볼, 실행한 검사와 그 결과를 기록한다. 긴 출력은 다시 찾을 위치나 명령을 남길 수 있다.
- 이미 시도했다가 실패한 방법과 아직 해결하지 못한 문제를 구분한다. 다음에 실행할 명령이나 수정을 구체적으로 적는다.

같은 오류가 로그에 자주 나타난다는 이유만으로 메모를 길게 할 필요는 없다. 반대로 딱 한 번 나온 경로나 사용자의 조건은 빠지면 다음 행동을 바꿀 수 있다. 어떤 내용을 남길지 결정하는 기준은 메모를 쓴 뒤에 할 일이다(부록 A).

### 한 번의 길이와 작업 전체의 길이

여러 대화를 이어 쓰면 ‘토큰을 적게 썼다’는 말만으로는 무엇이 줄었는지 알기 어렵다. 표 2의 최대 컨텍스트는 과제 하나를 푸는 동안 가장 길었던 단일 호출의 컨텍스트다. 부록 C의 전체 길이는 각 대화가 끝날 때의 길이를 합친 값이다. 두 번째 값은 여러 호출에서 같은 접두부를 몇 번 재사용했는지까지 합산한 API 과금 토큰 수와도 다르다.

가령 에이전트가 메모를 세 번 넘기면서 일하면 짧은 창으로도 긴 과정을 마칠 수 있다. 메모에 중요한 사실을 빠뜨려 같은 파일을 반복해서 읽으면 전체 작업은 오히려 길어진다. 따라서 ‘작은 창에 들어간다’, ‘빨리 끝난다’, ‘돈이 적게 든다’는 각각 따로 확인해야 한다.

## 실험 결과

### 코드 수정과 여러 단계의 작업

두 상용 모델을 여섯 벤치마크에서 평가했다. 아래 표는 전체 이력을 쓴 경우와 여섯 과제 모두에 1만 6천 / 1만 2천 토큰 설정을 적용한 경우를 비교한다. 과제마다 잘 나온 설정을 따로 고르면 가려질 수 있는 하락폭도 보인다. 표의 각 칸은 해당 과제에서 성공한 비율이다(부록 C, 표 3~8).

| 과제 | Opus 전체 이력 | Opus 임계값 정리 | GPT 5.6 Sol 전체 이력 | GPT 임계값 정리 |
|---|---:|---:|---:|---:|
| SWE-bench Verified, 코드 수정 | 70.0% | 68.8% | 84.4% | 84.6% |
| SWE-bench Multilingual, 여러 언어의 코드 수정 | 66.3% | 64.3% | 79.3% | 77.7% |
| Terminal-Bench 2.1, 터미널 작업 | 47.2% | 48.3% | 87.6% | 85.4% |
| FRAMES, 여러 위키백과 문서를 이용한 답변 | 81.0% | 79.6% | 90.2% | 87.1% |
| BFCLv3, 여러 차례 대화하며 도구 실행 | 62.0% | 61.5% | 39.5% | 39.0% |
| τ²-bench, 사용자 상담과 환경 상태 변경 | 79.3% | 79.3% | 73.9% | 74.5% |

컨텍스트를 조금 더 허용하면 결과가 달라졌다. SWE-bench Verified에서 Opus는 전체 상한 2만 4천, 임계값 1만 8천 토큰일 때 74.8%로 가장 높았다. GPT 5.6 Sol의 최고 해결률은 상한 4만 8천, 임계값 3만 6천 토큰에서 88.8%였다. Terminal-Bench에서는 Opus가 3만 2천 / 2만 4천 토큰에서 52.8%를 기록해 전체 이력보다 5.6%p 높았다. 한 모델에서 잘 맞은 설정이 다른 모델에서도 최고가 되지는 않았다.

여섯 과제의 설정 22개를 모두 보면 전체 이력 대비 변화는 Opus가 −3.7~+5.6%p, GPT가 −3.3~+4.4%p였다. 각 모델에서 2%p 넘게 하락한 설정은 5개 이하였다. 여러 문서에서 근거를 이어 답을 구하는 FRAMES에서는 두 모델 모두 모든 설정에서 전체 이력을 쓸 때보다 점수가 낮았다. 코드 수정에서 얻은 최고 해결률만 보면 FRAMES에서 일관되게 나타난 하락을 놓친다.

### 문서에서 필요한 구절을 찾는 과정

부록 E에서 에이전트는 칼라망어 문장에 들어 있는 동사 `kademor`를 문법서에서 검색했다. 검색 결과에는 그 단어가 들어 있는 3840번째 줄이 있었다. 에이전트가 이어서 읽은 범위는 3835~3870번째 줄, 모두 36줄이다. 그 안에는 단어의 뜻뿐 아니라 목적어를 도입하는 문법 설명과 실제 예문이 있었다. 파일 검색은 약 1만 9천 줄을 훑었지만 그 내용 전체가 모델의 입력으로 들어가지는 않았다.

자료의 이름을 확인하는 데만 원문이 필요한 경우도 있다. LOONG의 인용 관계 문제에서는 세 논문 가운데 두 파일에서 ‘OpenMoE’를 검색했다. 한 파일의 참고문헌에서 해당 제목을 찾은 뒤, 인용한 논문이 어느 것인지 확인하려고 그 파일의 첫 1천 자를 읽었다. AA-LCR의 다른 문제는 방송업을 제외한 업종별 위반 건수를 물었다. 이때에는 보고서에서 숫자가 나오는 줄을 찾는 것만으로 부족했다. 업종, 기간, 특정 회사의 반복 위반에 대한 설명을 함께 읽어야 제외 조건을 적용할 수 있었다.

| 긴 입력 벤치마크 | 평가 지표 | Opus 전체 입력 → 선택 읽기 | GPT 전체 입력 → 선택 읽기 |
|---|---|---:|---:|
| LongBench v2 | 객관식 정답률 | 68.0% → 67.6% | 70.8% → 72.6% |
| LOONG | 평균 점수 | 70.1% → 79.3% | 79.3% → 82.7% |
| AA-LCR | 여러 문서 추론 정답률 | 65.0% → 84.0% | 82.0% → 83.0% |
| NIAH | 숨겨 둔 사실의 정답률 | 60.0% → 100% | 80.0% → 100% |
| RULER | 필요한 답 가운데 찾은 비율의 평균 | 62.5% → 95.7% | 65.5% → 96.4% |
| Counting-Stars | 요청한 값이 모두 일치한 비율 | 65.1% → 81.2% | 76.6% → 81.2% |
| BABILong | 흩어진 사실을 연결한 답의 정답률 | 67.1% → 92.0% | 70.7% → 94.0% |

선택 읽기의 상한과 임계값은 NIAH가 4만 8천 / 3만 6천 토큰, 나머지는 1만 6천 / 1만 2천 토큰이다(표 11~17). LOONG에서 위와 같은 설정으로 만점을 받은 답의 비율도 Opus는 38.9%에서 53.4%, GPT는 44.4%에서 51.9%로 늘었다. 반면 LongBench v2의 Opus는 정답률이 0.4%p 낮았다. 자료를 짧게 읽을 수 있다는 사실만으로 정확도가 얼마나 달라질지 예측하기는 어렵다.

NIAH와 Counting-Stars에서는 메모를 쓰라는 조건이 한 번도 발동하지 않았다. 검색 결과와 주변 구절만으로 답을 낼 수 있었기 때문이다. 원문을 파일로 주는 것과 대화를 정리하는 것을 한 실험에 묶었지만, 이 두 과제의 성적 향상은 선택 읽기에서 나왔다. 특히 NIAH는 질문과 숨은 문장 사이에 같은 단어나 그 유의어가 있어 검색에 유리했다. 문서 곳곳의 표현을 해석해 종합해야 하는 과제에는 검색으로 찾은 여러 근거를 연결하는 과정이 더 필요하다.

### 매번 대화를 새로 열었을 때

SAC에서는 실행 결과를 받은 모델이 다음 호출에 넘길 상태를 갱신한다. 모델은 새 대화에서 그 메모를 읽고 한 번 행동한다. 긴 대화를 유지하지 않는 극단에서도 코드 수정과 검사를 끝까지 수행할 수 있는지 살펴본 실험이다.

| 모델과 과제 | 전체 이력 해결률 | SAC 해결률 | 과제별 최대 컨텍스트의 중앙값, 전체 이력 → SAC |
|---|---:|---:|---:|
| Opus, SWE-bench Verified | 70.0% | 70.2% | 3만 2천 → 8천 토큰 |
| Opus, Terminal-Bench 2.1 | 47.2% | 51.8% | 2만 7천 → 9천 토큰 |
| GPT, SWE-bench Verified | 84.4% | 82.4% | 1만 8천 → 7천 토큰 |
| GPT, Terminal-Bench 2.1 | 87.6% | 84.3% | 1만 7천 → 8천 토큰 |

표의 7천~9천 토큰은 모든 호출에 적용한 상한이 아니다. 과제별로 가장 길었던 호출을 하나씩 뽑아 중앙값을 구했다. 가장 길었던 사례까지 보면 SAC에서도 1만 5천~3만 7천 토큰에 이른다. 네 조합 모두에서 SAC는 임계값을 조정한 EoCC의 최고 성적보다 낮았다. 두 모델 모두 행동 사이에 짧은 기록만 넘겨받고도 상당수 과제를 마쳤다(표 2).

## 비용을 읽는 법

입력이 길면 다음 토큰 하나를 생성할 때 참조하는 과거 정보도 많아진다. 연구진은 H100에 공개 가중치 모델을 올리고 기존 입력의 KV cache를 재사용했다. KV cache는 이미 읽은 토큰에서 계산한 키와 값을 저장해 다음 토큰을 생성할 때 다시 쓰는 메모리다. 연구진은 요청마다 1,024개 토큰을 생성하도록 하고 요청을 동시에 몇 개 처리할지 바꿔 가장 높은 디코딩 처리량을 측정했다. GPU 한 대의 시간당 비용은 3.85달러로 잡았다(2.5절, 그림 1과 4).

| 모델 | 같은 GPU에서 출력 100만 토큰을 생성하는 비용, 25만 6천 토큰 상한 / 1만 6천 토큰 상한 |
|---|---:|
| GLM 5.2 | 3.6배 |
| Kimi K2.6 | 5.6배 |
| Qwen 3 Coder Next | 7배 |

여기서 7배는 Qwen의 특정 배포 조건에서 얻은 출력 단가의 차이다. 사용자가 하나의 작업을 맡겼을 때 내는 API 요금에는 처음 읽는 입력, 재사용한 입력, 생성한 출력의 양이 모두 들어간다. 짧은 창으로 여러 번 재시작하면 메모를 쓰느라 생성 토큰이 늘 수 있다. 반대로 긴 접두부를 매번 읽는 양은 줄 수 있다. 어느 쪽의 영향이 더 큰지는 모델과 과제에 달렸다.

부록 B는 짧은 창의 처리량 이득이 판매 단가에 반영된다는 가정으로 비용을 한 번 더 계산했다. 공개 가중치 모델 세 개에서 측정한 비용 비율의 평균을 반올림해, 1만 6천 토큰 상한에서 기준 단가의 20%를 적용했다. 그보다 큰 상한에서는 기준 단가까지 선형으로 올린다. 전체 이력 비용을 짧은 창의 추정 비용으로 나눈 값은 장기 작업에서 Opus가 2.2~8.8배, GPT가 2.4~5.0배였다. 긴 입력 과제에는 필요한 구절만 읽은 효과까지 반영돼 절감 배수가 각각 6.5~54.6배, 4.4~233.3배였다.

같은 실행을 두 단가로 계산한 예가 표 3에 있다. SWE-bench Verified 전체에서 GPT가 전체 이력을 쓴 비용은 공개 단가 기준 167.68달러였다. 1만 6천 / 1만 2천 토큰 설정에서는 공개 단가로 **203.12달러**, 가상의 짧은 창 단가로는 **40.62달러**였다. GPU에서 토큰을 생성하는 비용은 줄일 수 있어도, 이 작업을 공개 API 단가로 계산하면 전체 이력을 썼을 때보다 비용이 늘었다.

## 한계와 후속 연구

### 모델에 따라 달라지는 실패

공개 가중치 모델 다섯 개로 코드를 수정했을 때는 모델마다 상한을 낮춘 영향이 달랐다. 아래 값은 SWE-bench Verified 해결률이다. 연구진은 DGX Spark에서 양자화한 모델을 실행했다. 첫 번째 EoCC 설정의 임계값은 상용 모델 실험에서 쓴 3만 6천과 다른 4만 토큰이다(부록 D, 표 9).

| 모델 | 전체 이력 | 4만 8천 / 4만 토큰 | 3만 2천 / 2만 4천 토큰 | 1만 6천 / 1만 2천 토큰 |
|---|---:|---:|---:|---:|
| Qwen 3.6 27B | 68.6% | 69.4% | 68.2% | 65.0% |
| Qwen 3 Coder Next | 53.0% | 49.2% | 40.4% | 3.6% |
| Gemma 4 31B | 65.2% | 65.0% | 65.8% | 58.0% |
| Step 3.7 Flash | 70.0% | 66.8% | 64.6% | 56.6% |
| MiniMax M2.7 | 72.6% | 73.0% | 73.2% | 67.8% |

저자들은 Qwen 3 Coder Next가 한 단계에서 출력을 길게 쓰는 경향에 주목한다. 한도를 낮추자 메모를 남기고 다시 일을 시작한 뒤 얼마 지나지 않아 다음 메모를 써야 했다. 같은 모델이 Terminal-Bench에서는 가장 좁은 설정에서도 전체 이력의 29.2%와 비슷한 30.3%를 기록했다(표 10). 하드웨어 실험에서 짧은 창의 비용 이득이 가장 컸던 모델이기도 하다. 토큰 하나를 싸게 만드는 것과 문제가 풀릴 때까지의 비용은 이렇게 다른 방향으로 움직일 수 있다.

### 놓친 사실을 되찾을 수 있는 조건

논문에는 도구가 동전을 던질 때마다 결과를 알려 주는 예가 나온다. 지금까지 앞면이 몇 번 나왔는지만 기록하면 합계는 답할 수 있다. 나중에 사용자가 특정 순번의 결과를 물으면 그 기록으로는 답을 복원할 수 없다. 원문 3.1절은 이 예로 크기가 제한된 메모에서 생기는 정보 손실을 설명한다. 원래 실행 이력이 따로 남아 있고 필요한 대목을 찾아올 수 있다면 그때는 과거 기록을 검색하는 문제로 바뀐다.

실제 사용자가 중간에 요구를 바꿀 때도 비슷한 일이 생긴다. 처음 목표만 보면 버려도 될 것 같았던 조건이 새 요청에는 결정적일 수 있다. 부록 A는 에이전트가 처음 받은 목표대로 일하는 경우와 사람이 중간에 요구를 바꾸는 경우를 구분한다. 이번 결과로 설명할 수 있는 범위는 실험한 모델, 과제, 파일 접근 조건까지다.

연구진은 행동과 행동 사이에 넘기는 이 메모를 모델 훈련의 대상으로 삼자고 제안한다. SSSM은 원래 과제와 자연어 상태를 읽고, 행동한 결과를 반영해 다음 호출이 이해할 상태를 다시 쓰는 모델 구상이다. 일반적인 상태 공간 모델이 토큰 사이에 내부 수치 상태를 넘기는 것과 달리 사람이 읽을 수 있는 문장을 행동 사이에 넘긴다. 논문에서 측정한 것은 기존 모델에 SAC를 적용한 결과다. 이런 방식으로 새 모델을 훈련했을 때의 성능이나 학습 비용은 후속 연구로 남았다.

## 핵심 용어

| 용어 | 뜻 |
|---|---|
| FHA (Full-History Accumulation) | 한 과제가 끝날 때까지 같은 대화에 이력을 쌓는다. |
| EoCC (End-of-Conversation Compaction) | 대화가 임계값에 이르면 다음 단계에 쓸 메모를 작성하고 다시 시작한다. |
| SAC (Single-Action Compaction) | 환경에서 행동을 한 번 마칠 때마다 자연어로 상태를 갱신한다. |
| peak length | 한 과제에서 가장 길었던 단일 대화의 길이. 여러 대화의 누적 길이와 구분한다. |
| SSSM (Semantic State Space Model) | 행동 사이에 넘길 자연어 상태를 쓰도록 모델을 훈련하자는 제안이다. |
