## 요약

GeekNews에 올라온 gstack 소개 글이다. 작성자는 xguru이며, gstack을 "YC CEO Garry Tan이 만든 오픈소스 소프트웨어 팩토리"로 귀속하고 개인이 AI로 20인 팀처럼 일하게 해주는 도구라고 소개한다. 라이선스는 MIT로 명시한다.

이 자료가 담는 것은 두 층이다. 하나는 gstack의 기능 지도로, 스프린트 사이클과 명령어 구조, 스킬 목록, 파워 툴을 한 화면 분량으로 압축한다. 다른 하나는 커뮤니티 반응으로, 독자 댓글 4건을 함께 싣는다. 후자가 이 자료의 고유한 값이다. 저장소 문서만으로는 알 수 없는 한국 개발자 커뮤니티의 첫 반응이 여기에 기록되어 있다.

읽는 순서로는 원 저장소를 정리한 [[agents/garrytan-gstack]]을 먼저 보고 이 페이지를 나중에 보는 편이 낫다. 이 글은 저장소 문서를 압축한 소개이므로 명령어의 동작 원리나 설치 절차는 담지 않는다. 그 층은 저장소 페이지가 담당한다.

## 배경

gstack이 겨냥하는 문제 인식은 이 글 자체에 서술되어 있지 않다. 이 글은 도구가 무엇을 하는지만 나열하는 소개 형식이기 때문이다.

문제 인식의 근거는 같은 저장소를 다룬 [[agents/garrytan-gstack]]에 있다. 그 페이지는 기본 Claude Code가 똑똑하지만 한 가지 모드로만 응답한다는 점을 출발점으로 적고, 코드를 짜달라고 하면 곧장 짜기 시작할 뿐 만드는 것이 맞는지 먼저 되묻지 않는다고 서술한다. Garry Tan이 이를 역할의 부재로 규정했다는 정리도 그 페이지에 있다.

이 배경을 알고 나면 이 소개 글의 구성이 읽힌다. 명령어 목록을 사이클 순서로 늘어놓고 각 명령어에 사람 직함을 붙인 것은 기능 나열이 아니라 분업 구조의 제시다. 실제 팀에서 CEO가 방향을 정하고 엔지니어링 매니저가 설계를 확정하며 QA가 검증하는 순서를, 혼자 쓰는 도구 안에 다시 구현한 것이 gstack의 골격이다.

이 글이 gstack을 소프트웨어 팩토리라고 부르는 이유도 같은 지점에 있다. software factory는 반복 가능한 파이프라인으로 소프트웨어를 생산하는 체계를 뜻한다. 개인의 즉흥적 작업 대신 정해진 공정을 매번 통과시키겠다는 선언이다.

## 핵심 개념

스프린트 사이클은 이 글이 gstack의 뼈대로 제시하는 순서다. `Think → Plan → Build → Review → Test → Ship → Reflect` 일곱 단계이며, 이 글은 슬래시 명령어가 이 사이클 전체를 덮는다고 적는다. 사이클의 일부만 자동화하는 도구가 아니라는 주장이 여기에 담긴다.

슬래시 명령어는 Claude Code에서 특정 작업을 트리거하는 `/명령어` 단위다. gstack에서 이 단위는 기능 하나가 아니라 담당자 한 명에 대응한다. 이 글은 각 명령어가 역할별 전문가로 동작한다고 명시하며 CEO 리뷰어, 엔지니어링 매니저, 디자이너, QA 리드, 릴리즈 엔지니어 다섯을 든다.

스킬은 특정 작업 절차를 담아 에이전트에 결합하는 지침 패키지다. 이 글은 gstack이 제공하는 스킬을 이름 단위로 나열하는데, 명령어보다 넓은 목록이라 명령어로 노출되지 않은 기능까지 드러난다.

Conductor는 격리된 워크스페이스에서 Claude Code 세션을 병렬 실행하는 도구다. 이 글은 Conductor 기반 병렬 스프린트를 주목 기능으로 따로 떼어 강조한다.

## 스프린트 사이클과 명령어 배치

### 사이클 일곱 단계

이 글은 사이클 이름을 한 줄로 제시한 뒤 명령어를 별도 항목으로 묶어 적는다. 단계마다 명령어를 하나씩 지정하는 방식이 아니다. 따라서 아래 대응은 이 글이 명시한 짝과 명령어 이름으로 짚을 수 있는 짝을 구분해 표시한다.

| 단계 | 이 글에서 짝지을 수 있는 명령어 | 근거 |
|---|---|---|
| Think | `/office-hours` | 이 글이 제품 가설 검증으로 명시 |
| Plan | `/plan-ceo-review`, `/plan-eng-review` | 이 글이 아키텍처 확정으로 명시 |
| Build | 없음 | 명령어 목록에 대응 항목이 없다 |
| Review | `/review` | 명령어 이름으로 짚은 대응 |
| Test | `/qa` | 명령어 이름으로 짚은 대응 |
| Ship | `/ship` | 명령어 이름으로 짚은 대응 |
| Reflect | 없음 | 명령어 목록에 없고 스킬 목록에 회고가 있다 |

Build 단계에 붙는 명령어가 목록에 없다는 점은 도구의 무게중심을 보여준다. 코드를 작성하는 일은 Claude Code가 이미 하는 일이므로 gstack이 따로 명령어를 둘 필요가 없다. gstack이 추가하는 것은 작성 전후의 절차다.

### 명령어 묶음과 담당

이 글이 적은 명령어는 세 묶음이다. 각 묶음에 붙은 기능 서술은 이 글의 표현을 그대로 옮긴 것이다.

| 명령어 묶음 | 이 글이 적은 기능 |
|---|---|
| `/office-hours` | 6가지 강제 질문으로 제품 가설을 검증한다 |
| `/plan-ceo-review`, `/plan-eng-review` | 아키텍처를 확정한다 |
| `/review`, `/qa`, `/ship` | 버그 수정과 PR 생성을 자동화한다 |

세 묶음의 배치가 사이클 순서를 그대로 따른다. 첫 묶음이 코드를 쓰기 전의 검증이고, 둘째 묶음이 설계 확정이며, 셋째 묶음이 코드를 쓴 뒤의 처리다. 즉 gstack의 명령어는 구현 자체가 아니라 구현의 앞뒤를 감싼다.

`/office-hours`의 질문 수가 6가지로 고정되어 있다는 점은 이 글이 유일하게 제시하는 정량 표현이다. 질문 내용이 무엇인지는 적지 않는다.

### 역할별 전문가

이 글은 명령어와 역할의 대응 관계를 항목별로 명시하지 않고 다섯 역할을 한 줄로 열거한다. 아래 대응은 역할 이름과 명령어 이름의 일치로 짚은 것이다.

| 역할 | 이름으로 짝지을 수 있는 명령어 |
|---|---|
| CEO 리뷰어 | `/plan-ceo-review` |
| 엔지니어링 매니저 | `/plan-eng-review` |
| 디자이너 | 명령어 목록에 없다. 스킬 목록의 design 리뷰가 대응한다 |
| QA 리드 | `/qa` |
| 릴리즈 엔지니어 | `/ship` |

역할 집합이 여기서 끝나지 않는다는 점은 이 글 바깥에서 확인된다. [[agents/garrytan-gstack]]은 스태프 엔지니어와 보안 책임자를 포함한 더 넓은 역할 집합을 적고 각 역할에 대응하는 명령어를 단계별로 표로 정리한다. 이 소개 글은 그중 대표 다섯만 골라 실은 셈이다.

## 스킬 카탈로그

이 글이 적은 스킬 목록은 명령어 목록보다 넓다. 명령어로 노출되지 않은 기능이 스킬 이름으로만 등장하는 자리가 여기다.

목록은 나열 형태로만 제시되므로 아래 묶음은 이름을 기준으로 정리한 것이다. 이 글이 이런 분류를 제시한 것은 아니다.

| 묶음 | 스킬 |
|---|---|
| 기획과 검증 | office hours |
| 계획 리뷰 | CEO 리뷰, eng 리뷰, design 리뷰 |
| 조사와 품질 | investigation, QA, 보안 감사 |
| 출시와 운영 | 배포, canary 모니터링 |
| 계측과 기록 | 벤치마킹, 문서화, 회고 |

목록에서 눈에 띄는 항목은 canary 모니터링과 벤치마킹이다. canary 모니터링은 배포한 변경을 일부 구간에 먼저 노출해 이상을 감시하는 절차를 말한다. 두 항목 모두 코드를 출시한 다음의 운영 영역에 속하므로, gstack이 다루는 범위가 개발 사이클을 넘어 배포 후까지 이어진다는 것을 보여준다.

보안 감사와 문서화도 같은 성격이다. 결과물이 diff에 잘 드러나지 않아 개인 작업에서 가장 먼저 생략되는 절차들이며, gstack은 이를 이름 붙은 스킬로 만들어 호출 가능한 단위로 바꾼다.

## 파워 툴과 안전 가드

이 글은 명령어와 스킬 외에 파워 툴이라는 별도 묶음을 둔다. 네 가지가 들어 있다.

| 파워 툴 | 내용 |
|---|---|
| 독립 코드 리뷰 | Codex를 통해 별도 모델이 코드를 다시 검토한다 |
| 안전 가드 | `/careful`, `/freeze`, `/guard` |
| 배포 셋업 | 배포 환경 구성 |
| 버전 업그레이드 | 버전 올리기 |

Codex 리뷰의 성격은 이름 그대로 독립성에 있다. 코드를 작성한 모델이 아닌 다른 모델이 검토를 맡으면, 작성자가 스스로 놓친 지점을 잡을 가능성이 올라간다. 이 글은 이 기능을 슬래시 명령어 형태로 적지 않는다. 저장소를 정리한 [[agents/garrytan-gstack]]은 같은 기능을 `/codex`라는 명령어로 기록하며 OpenAI Codex CLI를 부르는 교차 리뷰라고 설명한다.

안전 가드 세 개도 이 글은 이름만 적는다. 각각의 동작은 [[agents/garrytan-gstack]]이 다음과 같이 기록한다.

| 명령어 | 저장소 페이지가 적은 동작 |
|---|---|
| `/careful` | 되돌리기 어려운 명령을 경고한다 |
| `/freeze` | 수정 범위를 잠근다 |
| `/guard` | 앞의 두 가지를 함께 적용한다 |

세 명령어의 공통 목적은 에이전트의 변경 범위를 제한하는 것이다. 자동화 수준이 올라갈수록 잘못된 변경이 번지는 비용도 함께 커지므로, 규율을 강제하는 도구는 제동 장치를 같이 갖춰야 한다.

## 병렬 스프린트

이 글이 주목 기능으로 따로 떼어 강조하는 것은 Conductor를 통한 병렬 스프린트다. 격리된 워크스페이스에서 여러 Claude Code 세션을 동시 실행하는 기능이다.

격리가 이 기능의 전제다. 세션이 같은 작업 디렉터리를 공유하면 서로의 변경을 덮어쓰므로, 세션마다 독립된 워크스페이스를 주어야 병렬 실행이 성립한다.

이 기능이 다른 항목과 성격이 다른 이유는 확장하는 대상에 있다. 명령어와 스킬이 한 세션 안에서 절차를 늘리는 장치라면, 병렬 스프린트는 세션 자체의 수를 늘린다. 20인 팀이라는 이 글의 비유가 실제 동시성으로 이어지는 지점이 여기다.

동시 실행 가능한 세션 수는 이 글에 없다. 그 수치는 저장소 자료가 담당한다.

## 대상 사용자

이 글은 대상 사용자를 세 부류로 나눈다. 소개 글에서 가장 구체적인 부분이며, 같은 도구가 사용자에 따라 다른 이유로 쓰인다는 점을 드러낸다.

| 대상 | 필요로 하는 것 |
|---|---|
| 코드를 짜는 기술 창업자와 CEO | 혼자서도 팀 규모의 산출을 내는 수단 |
| Claude Code 입문자 | 구조화된 워크플로 |
| 테크 리드와 스태프 엔지니어 | 엄격한 리뷰와 릴리즈 자동화 |

세 부류가 원하는 것이 서로 다르다. 창업자에게는 산출량이, 입문자에게는 따라갈 절차가, 테크 리드에게는 검증의 엄격함이 필요하다. gstack은 이 셋을 같은 명령어 집합으로 제공한다. 사이클 전체를 덮는 설계가 이런 다목적성을 가능하게 한다.

입문자를 대상에 포함한 점은 특히 눈에 띈다. 구조화된 워크플로가 필요하다는 서술은 gstack을 숙련자용 고급 도구가 아니라 절차 학습 도구로도 보고 있다는 뜻이다.

## 커뮤니티 반응

정량 지표가 없는 소개 글에서 반응 정보가 그 자리를 대신한다. 이 글은 독자 댓글 4건을 요지만 한 줄씩 기록한다.

| 발화자 | 요지 |
|---|---|
| kgcrom | Garry Tan이 X에서 이 글을 리트윗했다 |
| laeyoung | office-hours 스킬의 마크다운 문서가 방대하다 |
| angrybird0 | 1인 창업가를 위한 진화라는 점을 강조한다 |
| ragingwind | 유사 도구의 실사용 경험을 언급한다 |

네 반응의 성격이 각각 다르다. 첫 번째는 원 저자의 인지라는 외부 신호이고, 두 번째는 실제 설치 단계에서 나온 관찰이며, 세 번째는 도구의 의미 부여이고, 네 번째는 대안과의 비교다.

laeyoung의 관찰은 실무 비용을 짚는다. 스킬 문서가 방대하다는 것은 그만큼 컨텍스트를 차지한다는 뜻이며, 규율을 촘촘하게 만들수록 로드 비용이 커지는 구조적 긴장을 가리킨다. 같은 저자 계열의 자료를 정리한 [[agents/hada-2026-agent-skills]]에서도 800줄을 넘는 스킬의 컨텍스트 비용이 같은 방식으로 제기된다.

댓글 요지만 기록되어 있어 논거를 되짚을 수 없다는 점은 이 자료의 구조적 한계다. ragingwind가 언급한 유사 도구가 무엇인지, 어떤 경험이었는지는 이 자료에서 확인되지 않는다.

이 분업은 [[overviews/gstack-ai-software-factory-overview]]가 세 한국어 자료의 성격을 비교한 정리를 따른 것이다. 그 페이지는 이 GeekNews 글을 커뮤니티 소개로, 나머지 둘을 각각 명령어 카탈로그와 실전 가이드로 자리매김한다.

## 한계

- 소개 글이라 세부 검증보다 요약과 전달에 초점이 있다. 명령어의 동작 방식, 설치 절차, 성능 수치가 없다.
- 정량 지표가 하나도 없다. 도구가 실제로 생산성을 올리는지는 이 자료만으로 판단할 수 없다.
- 명령어와 역할의 대응을 항목별로 명시하지 않는다. 이 페이지의 대응표 가운데 일부는 이름의 일치로 짚은 것이며 이 글이 선언한 짝이 아니다.
- 사이클 일곱 단계 가운데 Build와 Reflect에 대응하는 명령어를 적지 않는다.
- 댓글 4건이 요지만 남아 있어 발화자의 논거와 근거를 확인할 수 없다.
- 게시 시각은 원문 페이지의 상대 표기를 수집 시점에 환산한 값이라 정확한 날짜가 아니다.

## 핵심 용어

| 용어 | 뜻 |
|---|---|
| software factory | 반복 가능한 파이프라인으로 소프트웨어를 생산하는 체계. 이 글이 gstack을 소개하며 쓰는 표현이다 |
| office hours | 코딩에 들어가기 전 제품 가설을 질문으로 검증하는 gstack 스킬 이름 |
| Conductor | 격리된 워크스페이스에서 Claude Code 세션을 병렬 실행하는 도구 |
| canary 모니터링 | 배포한 변경을 일부 구간에 먼저 노출해 이상을 감시하는 절차 |
| 안전 가드 | 에이전트의 변경 범위를 제한하는 명령어 묶음. 이 글은 `/careful`, `/freeze`, `/guard` 셋을 든다 |
