## 요약

TASTE는 토스의 여러 서비스에서 한 사용자가 남긴 행동을 함께 학습해 두 가지 결과를 제공한다. 캠페인 담당자는 사용자별 행동 확률을 받아 메시지를 보낼 대상을 고른다. 쇼핑이나 미니앱처럼 별도의 추천 모델을 운영하는 팀은 사용자의 행동 이력을 숫자 벡터로 표현한 사용자 임베딩을 받아 자신의 예측에 활용한다.

두 방식의 차이는 푸시에서 잘 드러난다. 금융 상품 신청 가능성이 높은 사람에게 푸시를 보내려면 TASTE가 계산한 목표 행동 확률로 사용자를 정렬할 수 있다. 반면 특정 푸시를 누를 가능성을 추정하려면 푸시 클릭 모델이 TASTE 임베딩을 기존 입력과 함께 읽는다. 후자의 경우 TASTE가 처음부터 그 푸시의 클릭을 예측하도록 학습할 필요가 없다.

## 배경

토스에서 금융 상품에 관심을 보인 사람, 쇼핑 상품을 구매한 사람, 미니앱을 이용한 사람은 서로 겹친다. 서비스마다 예측할 행동은 다르지만 나이, 앱에서 사용한 기능, 소비 이력처럼 준비해야 하는 데이터는 비슷하다. 예측 모델을 개별적으로 운영하면 같은 사용자의 정보를 각 팀이 가공하고 학습하는 작업도 반복된다.

| 입력 원천 | 공통 사용자 표현을 만들 때 고려할 점 |
|---|---|
| 서버 로그 | 월간 활성 사용자가 2,000만 명을 넘고 주요 로그만 하루 수십억 건 이상이다. 개별 서비스 모델에서 읽어야 할 이력이 많다. |
| 마이데이터 | 수십 개 API에서 들어온다. API마다 정보가 수집되는 시점과 그 정보를 확보할 수 있는 사용자 범위가 다르다. |
| MMP 데이터 | 외부 앱 이용을 기록한다. 사용자에 따라 이벤트가 지나치게 많거나 드물어 이력의 밀도가 고르지 않다. |

세 원천은 분석과 활용에 필요한 동의 조건도 다르다. 더 많은 이력을 읽기 위해 서비스 모델을 키우는 데에는 응답 시간 제약이 따른다. 토스는 이런 조건에서 각 서비스가 놓치는 정보가 있을 수 있다고 보고, 여러 행동을 함께 예측하는 과정에서 공통으로 쓸 수 있는 사용자 표현을 학습했다.

## 공동학습의 범위와 모델 구조

### 100만 명으로 시작한 비교

공동학습 모델의 인코더는 사용자 입력을 과제들이 공유하는 표현으로 바꾼다. 그 뒤에는 금융 상품 이용이나 결제처럼 서로 다른 행동의 발생 여부를 예측하는 헤드가 붙는다. 첫 실험에 쓴 MMoE는 각 과제에서 필요한 정보를 서로 다른 비중으로 조합하도록 학습하는 구조다.

토스는 빠른 검증을 위해 사용자를 100만 명으로 제한했다. 이때 두 가지 비교가 가능하도록 기존 방식인 LightGBM도 같은 100만 명으로 다시 학습했다. 첫 비교는 기존 모델에서 학습 규모를 줄였을 때의 차이를, 두 번째 비교는 같은 사용자 수에서 공동학습과 개별 학습 사이의 차이를 보여준다.

| 학습 조건 | 평균 AUROC | 비교의 의미 |
|---|---:|---|
| 전체 사용자, 기존 모델 | 0.9218 | 사용자 수를 줄이기 전 성능 |
| 100만 명, 과제별 LightGBM | 0.9086 | 전체 사용자 조건에서 0.0132 하락 |
| 100만 명, MMoE 공동학습 | 0.9023 | 같은 규모의 LightGBM에서 0.0063 하락 |

AUROC는 실제로 행동한 사용자를 행동하지 않은 사용자보다 높은 점수에 두는 능력을 나타낸다. 100만 명 조건에서는 개별 모델이 앞섰다. 토스는 이 결과를 바탕으로, 여러 행동을 동시에 배우는 모델에 충분한 사용자 수와 행동 이력을 제공했을 때에도 같은 차이가 나타나는지 실험했다.

### 요약 정보와 행동 순서의 결합

확장 실험에서는 학습 대상을 이용 가능한 전체 사용자로 넓히고, 사용자당 요약 정보도 약 1,000개에서 2,000개 이상으로 늘렸다. 요약 정보에 담기지 않은 시간 순서를 보존하기 위해 최근 앱이벤트를 별도의 입력으로 추가했다.

| 단계 | 입력을 처리하는 방법 |
|---|---|
| 사용자 요약 | DCN-V2 인코더가 사용자별 요약 정보를 읽는다. |
| 행동 순서 | Causal Transformer가 최근 앱이벤트를 시간순으로 읽고 압축한다. |
| 표현 결합 | Gated Fusion이 요약 정보와 행동 이력에서 얻은 두 표현을 결합한다. |
| 과제별 예측 | PLE가 결합한 사용자 표현을 받아 앱이벤트별 발생 확률을 계산한다. |

![[assets/park-2026-taste-toss-recommendation-foundation-platform/fig05.png]]
*Figure 5: 요약 정보와 시간순 앱이벤트를 결합하는 구조 및 시퀀스 포함 여부에 따른 성능 차이 (토스, 2026)*

상위 5,000명을 고르는 타기팅 과제에서는 실제로 목표 행동을 한 사용자 중 선택한 명단에 포함된 비율을 구할 수 있다. 이 recall을 앱이벤트별로 구한 뒤 평균한 지표가 원문의 Macro Recall@5k다. <!-- lint-style: ignore --> <!-- 원문 지표명 -->

공통 앱이벤트에서 이 지표는 기존 모델의 16.43%에서 확장한 TASTE의 22.19%로 높아졌다. 절대 차이는 5.76%p이고 기존 값에 대한 상대 개선율은 약 35.1%다. 이 실험에서는 사용자 수와 입력, 모델 구조가 함께 바뀌었다.

행동 순서가 기여한 정도는 확장한 모델에서 시퀀스 모듈만 제거한 비교로 확인했다. 모듈을 포함한 성능을 100으로 두면 제외한 성능은 92.4로, 상대적으로 7.6% 낮았다. 따라서 2,000개 이상의 요약 정보를 사용한 조건에서도 최근 이벤트의 순서를 직접 읽는 것이 예측에 도움이 됐다.

### 소비 과제와 앱이벤트 과제의 분리

소비 예측을 추가하면서 토스는 입력과 학습 목표를 함께 확장했다. 입력에는 브랜드와 카테고리 등 소비 시퀀스를 읽는 인코더를 추가했고, 출력에는 미래 소비를 예측하는 헤드를 두었다. 하나의 사용자 표현으로 모든 과제를 학습했을 때 소비 예측은 기존 개별 모델보다 좋아졌지만 앱이벤트 예측은 앱이벤트들만 공동학습한 조건보다 낮아졌다.

앱에서 기능을 이용하는 행동과 소비는 성격이 다르고, 학습에 필요한 정답이 들어오는 시점도 다르다. 토스는 두 목적이 같은 입력에서도 서로 다른 표현을 필요로 한다는 가설을 시험했다. 두 모델 모두 사용자 요약 정보, 앱이벤트 이력, 소비 이력을 받는다. 다만 인코더부터 따로 학습해 하나는 여러 앱이벤트를, 다른 하나는 여러 소비 과제를 함께 예측한다.

![[assets/park-2026-taste-toss-recommendation-foundation-platform/fig07.png]]
*Figure 7: 공통 입력을 앱이벤트와 소비 모델에 각각 전달하는 구조 및 목적별 성능 변화 (토스, 2026)*

| 예측 목적 | 비교 대상 | 상위 5,000명 기준 과제 평균 recall의 상대 개선율 |
|---|---|---:|
| 앱이벤트 | 앱이벤트와 소비를 함께 학습한 단일 TASTE | 8.7% |
| 소비 브랜드 | 기존 운영 모델 | 33.9% |
| 소비 중분류 | 기존 운영 모델 | 111% |
| 소비 소분류 | 기존 운영 모델 | 65.8% |

앱이벤트의 8.7%는 단일 TASTE와 목적별 TASTE 사이의 차이다. 소비 수치의 기준은 기존 운영 모델이다. 모델을 나누면서 각 모델의 구조와 학습 방법도 목적에 맞춰 최적화했으므로 이 비교에는 그 변경의 효과가 함께 들어 있다.

## 예측 확률을 이용한 캠페인 운영

IM은 홈 상단 배너 노출과 푸시, SMS, LMS, 브랜드톡 발송을 관리하는 토스의 메시지 허브다. 기존에는 담당자가 목표에 맞는 행동 이력을 찾고 누구에게 보낼지 조건을 조합했다. Auto Targeting에서는 담당자가 목표 이벤트와 인원수를 고르면 IM이 TASTE의 예측 확률이 높은 사용자부터 발송 대상으로 정한다. 여러 과제의 데이터 준비와 학습, 추론도 함께 처리할 수 있다.

| 근거 | 비교 조건 | 결과 |
|---|---|---|
| 도입 후 두 달간 푸시 운영 집계 | 일반 캠페인과 Auto Targeting 캠페인 | 클릭률 4.39%와 5.19%, 발송 대비 전환율 0.25%와 2.70% |
| 금융 상품군 1의 LMS 온라인 실험 | 기존 타기팅 모델과 TASTE | TASTE에서 발송 수는 약 35% 감소하고 전환 건수는 약 40% 증가 |
| 금융 상품군 2의 홈 상단 배너 온라인 실험 | 기존 모델만 선정한 사용자와 TASTE만 선정한 사용자 | TASTE 쪽 클릭률은 1.72배, 최종 전환율은 4.75배 |

첫 행은 서로 다른 캠페인을 모아 본 운영 실적이다. 캠페인의 차이와 모델의 효과가 섞여 있으므로 두 비율의 차이 전체를 TASTE의 효과로 돌릴 수 없다. 상품군 1은 전환율이 아닌 **전환 건수**를 보고했고, 상품군 2의 배수는 각 모델에서만 선정한 사용자 집단 사이의 비교에 해당한다.

## 사용자 임베딩의 서비스 간 전이

기존 TASTE에 새 과제의 헤드를 추가하면 그 헤드의 학습 신호가 공통 인코더까지 전달된다. 기존 예측값도 달라질 수 있으므로 서비스 하나를 추가할 때마다 영향을 받는 과제를 다시 평가해야 한다. 토스는 이 운영 부담을 줄이기 위해 TASTE가 계산한 임베딩을 서비스 모델의 입력으로 제공했다. 서비스팀이 자기 모델을 학습하는 동안에는 TASTE의 가중치가 고정된다.

### 오프라인 평가

홈 배너와 푸시의 클릭 또는 전환을 예측하는 마케팅과 CRM 모델에서는 8개 모델 모두 기존 입력에 임베딩을 더했을 때 AUROC가 개선됐다. 다음 값은 원문 그림에 표시한 AUROC의 절대 차이다. 같은 종류의 전환과 클릭을 다루는 모델은 그림의 번호로 구분한다.

| 마케팅 및 CRM 예측 과제 | AUROC 차이 |
|---|---:|
| 혜택 지면 배너 클릭 | +0.0151 |
| 홈 상단 배너 전환 ① | +0.0100 |
| 홈 상단 배너 클릭 | +0.0058 |
| 리스트 배너 클릭 | +0.0052 |
| 푸시 클릭 ① | +0.0049 |
| 홈 상단 배너 전환 ② | +0.0035 |
| 푸시 클릭 ② | +0.0014 |
| 푸시 전환 | +0.0013 |

쇼핑과 광고에서는 각 대조군에 대한 상대 변화율을 보고했다. AUROC는 높을수록 좋고, NE는 예측 손실을 정규화한 값이어서 낮을수록 좋다. 쇼핑의 세 행은 하나의 구매 전환 모델이 함께 학습하는 세 목적이며, 최신 행동을 반영한 임베딩을 추가해 기존 운영 모델과 비교했다. 광고의 네 행은 각각 다른 예측 모델과 그에 대응하는 대조군의 비교다.

| 영역 | 예측 과제 | AUROC 증가율 | NE 감소율 |
|---|---|---:|---:|
| 쇼핑 | 관심 | 0.50% | 3.24% |
| 쇼핑 | 장바구니 추가 | 0.66% | 1.50% |
| 쇼핑 | 구매 | 0.27% | 0.54% |
| 광고 | 통합 클릭률 | 0.15% | 0.27% |
| 광고 | LightGBM 기반 클릭률 | 0.12% | 5.15% |
| 광고 | 리워드 광고 | 2.29% | 1.62% |
| 광고 | 비리워드 광고 | 0.21% | 0.14% |

### 미니앱 추천의 온라인 평가

미니앱 추천에서는 온라인 A/B 테스트로 실제 클릭을 측정했다. 추천 지면마다 기존 클릭률이 다르므로 같은 지면 안에서 기존 모델과 임베딩을 사용한 모델을 비교한다.

| 추천 지면 | 기존 모델 클릭률 | 임베딩 사용 모델 클릭률 | 상대 증가율 |
|---|---:|---:|---:|
| 전체 탭 | 1.56% | 2.77% | 약 77% |
| 최근 더보기의 ‘이런 건 어때요’ | 3.51% | 10.85% | 약 209% |

전체 탭에서는 최근 28일 동안 미니앱을 이용하지 않은 사용자도 별도로 살펴봤다. 이들에게 비앱테크 미니앱을 추천했을 때 TASTE 임베딩을 쓴 모델의 클릭률은 공통 사용자 피처를 쓴 모델의 약 2.5배였다. 미니앱 이용 이력이 없는 기간에도 토스의 다른 서비스에서 배운 정보가 해당 추천에 도움이 될 수 있음을 보여준다.

## 임베딩 평가와 한계

TASTE에서 앱이벤트 예측 성능이 좋아져도 쇼핑이나 광고 모델에서 같은 개선을 얻는다고 단정하기 어렵다. 서비스별로 효과를 확인하려면 팀마다 모델을 다시 학습해야 하고, 실제 반응을 확인하려면 온라인 실험도 필요하다. TASTE Bench는 서비스의 예측 문제를 재현한 프록시 모델을 사용해 온라인 실험을 기다리는 동안에도 다음 임베딩 후보를 평가한다.

![[assets/park-2026-taste-toss-recommendation-foundation-platform/fig11.png]]
*Figure 11: TASTE Bench에서 기존 입력 유지, 임베딩 추가, 사용자 피처 대체 조건을 비교하는 절차 (토스, 2026)*

| 비교 조건 | 서비스 모델에 주는 입력 | 확인할 내용 |
|---|---|---|
| 기존 입력 | 서비스가 쓰던 피처 | 과제별 비교 기준 |
| 임베딩 추가 | 기존 입력과 TASTE 임베딩 | 서비스가 이미 가진 정보에 무엇을 더하는가 |
| 사용자 피처 대체 | 기존 사용자 피처를 TASTE 임베딩으로 교체 | 서비스가 직접 준비하던 사용자 정보를 어느 정도 대신할 수 있는가 |

동일 조건에서 임베딩 후보를 바꿔 보면 앱이벤트, 푸시 클릭, 광고 클릭 등 어느 과제가 개선되거나 저하되는지 살펴볼 수 있다. 토스는 이 결과를 다음 학습에 반영한다. 현재까지 기존 피처에 임베딩을 추가하는 실험은 대부분 개선됐지만, 대체 실험에서는 일관된 우위를 확인하지 못했다. 이는 서비스팀이 기존 사용자 피처를 언제까지 유지해야 하는지 판단할 때 중요한 구분이다.

## 후속 과제

- **학습 입력 확대.** 토스는 소비와 앱 행동에 더해 광고, 쇼핑, 금융 거래에서 얻는 정보를 더 폭넓게 학습하고 있다. 서비스마다 공통 사용자 피처를 고르고 하나씩 추가하거나 제거해 보는 부담을 줄이는 것이 목표다.
- **사용자와 아이템의 관계 전달.** 핵심 도메인에서는 사용자 임베딩과 함께 학습한 아이템 임베딩, 사용자와 아이템 사이의 상호작용을 계산하는 모듈까지 전달하는 방식을 오프라인에서 실험하고 있다.
- **임베딩 갱신과 연결.** 사용자 이력이 같아도 임베딩을 생성하는 모델이 바뀌면 벡터의 좌표와 분포가 바뀔 수 있다. 토스는 갱신 주기, 표준화와 좌표 정렬, 날짜별 임베딩을 서비스 학습 데이터에 연결하는 방식을 비교하고 있다.

| 용어 | 뜻 |
