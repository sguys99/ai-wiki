- 문장을 자유롭게 생성하는 대신 미리 정한 형식의 값과 확률을 반환하며, 여러 판단 결과를 한 번의 요청에서 병렬로 출력함
- 각 답에 신뢰도와 불확실성을 함께 제공하도록 학습했으며, 정해진 스키마와 타입을 벗어나지 않도록 보장함

- 자체 워크플로 평가에서는 193.6배 빠르고 444.6배 저렴한 결과를 제시했지만, 실제 개선 폭의 상단에 가까운 수치이며 비교 모델의 출력 방식과 평가 구성에 영향을 받음

## 소프트웨어 자동화를 위한 System One Model

- TypeSafe AI는 2년간의 비공개 개발을 거쳐, 빠르고 구조화된 판단을 소프트웨어에 직접 전달하는 System One Model을 공개함
- 자동화에 초점을 맞춰 새 모델 아키텍처, 병렬 샘플러, 보정된 판단을 위한 강화학습인 RLCD(Reinforcement Learning for Calibrated Decisions)를 개발함
- 첫 공개 모델 Jev는 비정형 상태를 입력받아 타입이 정해진 확률적 판단을 반환하는 함수 호출처럼 동작함 

 - 문자열 생성을 포기하는 대신 구조화된 출력에 최적화함
 - TypeSafe는 System One 과제에서 기존 LLM과 비슷한 지능 수준을 유지하면서 속도와 효율을 약 두 자릿수 규모로 개선했다고 밝힘

- 출발점은 대화 능력이 뛰어난 모델이 등장했는데도 자동화가 충분히 확산하지 않았다는 문제의식이며, 목표는 소프트웨어가 의존할 수 있는 AI 인터페이스임

## 기존 LLM과 다른 학습 목표와 입출력

- 기존 LLM의 RLHF / RLVR는 사람이 선호하는 응답이나 프로그램으로 검증 가능한 보상을 최적화하지만, RLCD는 System One 과제에서 모델의 지식과 불확실성을 정직하게 반영하는 보정된 확률을 목표로 함
- 입력은 양쪽 모두 텍스트 같은 비정형 데이터를 받지만, 기존 LLM은 순차적 메시지에, Jev는 구조화된 프로그램 상태에 중점을 둠
- 출력의 자유도와 사용 방식이 다름 

 - 기존 LLM은 대화, 코드, 환각, 거부 응답, 타입 안전한 값 등 무엇이든 문자열로 생성할 수 있으며, 소프트웨어에서 사용하려면 파싱과 검증이 필요함
 - Jev는 [미리 정의한 출력과 구조](https://docs.typesafe.ai/) 안에서 타입 안전한 값만 반환하고, 모든 답에 보정된 확률과 신뢰도 점수를 함께 제공함

- 기존 LLM은 이전 토큰을 조건으로 한 토큰씩 생성하지만, Jev는 한 번의 질의에서 모든 출력을 병렬 생성하며 하드웨어 효율을 고려함
- 신뢰도는 자동화의 핵심 조건임 

 - 기존 모델은 신뢰도를 물어도 과신하거나 일관되지 않을 수 있으며, 과제를 95% 수행하더라도 실패하는 5%를 구분하지 못하면 자동화하기 어려움
 - Jev는 매 출력에서 불확실성을 전달하고, 높은 신뢰도가 높은 정확도에 대응하도록 보정하며, 유사한 입력에 더 일관된 답을 반환함

## 가격, 속도와 적합한 활용처

- Jev의 입력 가격은 100만 토큰당 0.042달러, 즉 10억 토큰당 42달러이며 출력은 무료임 

 - 비교표에 실린 기존 LLM의 입력 가격은 100만 토큰당 0.20~10달러이고, 출력은 입력보다 약 5배 비쌈
 - TypeSafe는 가격의 장기 지속 가능성은 시간이 지나야 입증할 수 있으며, 향후 가격은 상승보다 하락할 것으로 예상함

- 종단 간 응답 시간은 70~500ms임 

 - 비교에 사용한 [프런티어 모델 응답 시간 자료](https://llm-benchmarks.diegoromero.es/)는 3~329초이며, 비교표는 System One 형태의 질의에서 같은 수준의 지능을 기준으로 40~200배 빠르다고 명시함
 - 공개 평가 대부분은 서비스가 현재 위치한 미국 서부 해안에서 노트북으로 실행함

- 기존 LLM은 사람이 개입하는 작업과 검증 가능한 문제에 적합함 

 - 챗봇, 코파일럿, 코딩 에이전트는 강력하고 범용적이지만 자유로운 출력 때문에 사람의 감독이 필요함
 - 수학 증명과 커널 최적화처럼 정답을 저렴하게 자동 검증할 수 있는 작업은 생성, 테스트, 반복에 적합함
 - 문자열의 유연성은 항상 작동하지는 않는 빠른 프로토타입 제작에도 유용함

- Jev는 AI 워크플로와 유연한 조건 분기에 초점을 맞춤 

 - 수작업 규칙이 취약한 분류, 라우팅, 점수화, 추출, 분기에 구조화된 출력을 사용하며 주변 코드가 모델의 자유도를 제한함
 - 페타바이트 규모 데이터의 맵리듀스 처리로 특징과 인사이트를 추출하거나, 약 100ms 속도가 필요한 실시간 사용자 경험에 활용할 수 있음
 - LLM 프롬프트, 추론 기록, 출력의 점수화, 판정, 검증, 가드레일 적용과 탈옥 탐지에도 사용할 수 있음

## 나란히 실행한 데모의 결과와 조건

- [실제 데모 질의](https://console.typesafe.ai/playground?share=shr_13a74b495fb786c4bd7964f11597301e7c9)는 Jev가 확률을 병렬 출력하고 LLM은 토큰을 자기회귀적으로 생성하는 차이를 보여줌 

 - 얼리 액세스 사용자가 접근할 수 있으며, questions의 키는 화면에서 이해하기 쉬운 이름으로 구성함
 - state는 짧고 정보 밀도가 높은 문단으로 작성했으며, 짧은 입력은 Jev에 유리한 조건임

- 비교 대상은 기본 추론 설정의 GPT-5.6 Terra로, TypeSafe가 평균적으로 Jev와 가장 비슷한 지능 수준이라고 판단한 모델임
- 녹화된 실행에서 유일한 불일치는 고객 이탈 가능성 수준이었으며, TypeSafe는 해당 답 자체가 실제로 모호하다고 봄
- 비슷한 초기 데모가 System One Model 개발에 집중하기로 결정하는 계기가 됨

## 워크플로 평가 방법과 한계

- 평가는 정답 분류에 맞춰 모델과 하네스를 바꾸기보다, 올바른 계산 그래프인 동일한 코드 워크플로를 모든 모델에 적용함 

 - 하네스 엔지니어링을 통한 과적합 가능성을 피하고, 크고 성능이 높으며 비싼 외부 모델의 예측을 참조 확률로 사용함
 - 참조 답은 GPT-6 Astra와 Fable 5.1의 평균임

- Jev는 평가에서 거의 두 자릿수 규모에 걸쳐 파레토 프런티어를 차지함 

 - 워크플로의 모든 로직을 추론 과정에서 처리하도록 생성한 프롬프트와도 비교했지만, 이 방식은 워크플로 자체를 사용하는 것보다 대체로 성능이 크게 낮았음
 - 홈페이지의 193.6배 빠른 속도와 444.6배 낮은 비용은 이 평가에서 나왔으며, 실제 개선 폭의 상단에 가까운 결과일 것으로 예상함

- 공개한 4개 워크플로는 나란히 실행한 데모보다 복잡하며, 실제 비즈니스 자동화의 프로덕션 작업을 더 잘 반영함 

 - 신뢰성 높은 실제 워크플로는 독립적으로 분해한 여러 질문을 사용하고, 개별적인 확정 판단보다 확률에 따라 세밀하게 동작하는 경향이 있음
 - 최종 결과는 이산적인 분기지만, 그 결과에 도달하는 과정에는 높은 일관성이 필요한 도메인별 엔지니어링이 들어감
 - 예제, 불일치 사례, 전체 질의와 워크플로는 [워크플로 평가 사이트](https://evals.typesafe.ai/)에서 확인할 수 있음

- 평가 편향과 비교 비용에 관한 한계가 있음 

 - 워크플로는 모델에 유리하도록 의도적으로 고르거나 구성하지 않았고 학습 분포에도 없지만, 모델 역량 팀 구성원이 만들었으므로 편향 가능성이 있음
 - 참조 답이 OpenAI와 Anthropic 모델 쪽으로 치우치므로, TypeSafe는 Jev와 DeepSeek의 상대적 성능이 과소평가됐을 가능성이 있다고 봄
 - 비교 LLM은 [System One LLM 래퍼](https://github.com/typesafe-ai/system-one-adapter-python)를 사용해 API와 호환되는 구조화된 판단을 출력함
 - TypeSafe는 이 방식이 LLM에서 가장 정확하게 판단을 얻는 방법이라고 봤지만, 확률 없이 판단만 출력하는 것보다 느리고 비싼 경향이 있음

## 환각 방지와 타입 안전성 보장의 범위

- TypeSafe는 System One 과제에서 기존 LLM과 비슷한 판단 능력을 유지하면서 속도와 효율을 약 100배 높였다고 밝힘
- TypeSafe가 제시한 ‘환각 방지’의 근거는 미리 정의한 출력 형식과 타입을 벗어나지 않는다는 보장이며, 반환한 판단이 항상 정확하다는 뜻은 아님
- 타입 오류 0% 는 관측된 실험 결과가 아니라 스키마 일치 보장에 근거한 수치임 

 - TypeSafe는 타입 오류 발생이 수학적으로 불가능하다고 밝힘
 - 비교 LLM의 수치는 OpenRouter에서 가져왔으며, 복잡한 질의가 더 좋은 모델로 라우팅됐을 가능성 때문에 편향이 있을 수 있음

## Doom과 Wikiracing 데모

- Doom 데모는 코드와 AI를 결합해 실시간으로 게임 상태에 반응하고 지시를 따르는 모습을 보여줌 

 - 초당 10회 질의할 때 비용은 시간당 약 7달러임
 - 입력은 이미지가 아니라 텍스트를 포함한 구조화된 상태 데이터임
 - AI를 사용하지 않는 Doom 봇이 더 잘 플레이할 수 있지만, 이 데모의 목표는 다양한 상태 표현에 반응하고 지시를 따르는 봇임
 - 상세 해설 공개와 관련 개발 행사를 계획함

- Wikiracing은 Wikipedia 페이지에서 출발해, 탐색 중 만나는 링크만 따라 목표 페이지에 도달하는 게임임 

 - 한 단계에서 수백~수천 개 링크 중 선택해야 하므로, 초당 지능뿐 아니라 많은 선택지에서 환각 없이 판단하는 효과를 보여줌
 - 두 번째와 세 번째 도전이 모두 “Rubber Duck”에서 시작한 것은 팀이 아는 한 우연임

- Wikiracing의 속도 개선 폭은 다른 데모보다 작았으며, 비교 설정에 주의가 필요함 

 - 비교 LLM은 비추론 모드로 실행했고 Astra만 가장 낮은 추론 설정을 사용함
 - 시청하기 편하도록 설정한 조건이며, LLM은 추론을 켰을 때 이 작업을 훨씬 잘 수행함
 - 이 설정 차이는 Jev가 더 적은 단계로 완료한 경향의 이유이기도 함

- Jev는 최대 255개 선택지를 지원함 

 - 선택지가 더 많으면 독립적인 점수화 후 명시적으로 선택하는 2단계 방식을 사용하며, 이 때문에 가끔 느려짐

## 얼리 액세스와 이름의 유래

- [얼리 액세스](https://typesafe.ai/)를 열고 대기 명단의 개발자에게 가능한 한 빠르게 접근 권한을 제공하고 있음 

 - 자동화하려는 판단, Jev가 잘 작동하는 영역과 부족한 영역에 대한 피드백을 받고 있음

- System One Model이라는 이름은 Daniel Kahneman의 [Thinking, Fast and Slow](https://www.penguinrandomhouse.com/books/89308/thinking-fast-and-slow-by-daniel-kahneman/)에서 영향을 받음 

 - 빠르고 직관적인 System 1 사고와 느리고 숙고하는 System 2 추론의 구분에서 이름을 가져옴
 - System 1 사고에는 오류가 잦다는 의미도 있지만, TypeSafe는 System One Model을 대안보다 더 신뢰성 있게 만들 수 있다고 믿으며 그 근거는 추후 공개할 예정임

- Jev는 William Stanley Jevons의 이름에서 따옴 

 - 증기기관 효율 향상이 석탄 수요 증가로 이어졌듯 기계 지능도 비슷한 경로를 따를 것으로 예상함
 - 지능의 비용이 한 자릿수 규모씩 낮아질 때마다 활용처는 여러 자릿수 규모로 늘어날 것이라는 기대를 담음

- 흥미롭고 새로운 제품이지만, 제목은 범용 생성을 포기하고 빠른 타입 기반 추론을 택한 Jev 정도가 더 정확해 보임. 튜링 완전 언어로 코드를 출력하는 생성 모델은 컴퓨터가 할 수 있는 모든 일을 표현할 수 있는데, 구조화된 출력만 만드는 Jev와 속도를 비교하면 오해를 부를 수 있음.
 분류·라우팅·점수 산정에는 유용하겠지만, 지금 코드 작성과 자동화에 쓰는 모델과는 성격이 상당히 다름. 환각이 불가능하다는 표현도 부정확해 보임. 잘못된 타입은 출력하지 않더라도 타입만 유효한 완전히 틀린 값은 낼 수 있고, LLM도 적절한 실행·검증 장치를 붙이면 구조화된 출력을 강제할 수 있음. 눈속임이 없다면 Doom 데모는 멋짐. 

 - 여기서 환각이 불가능하다는 건 결과마다 신뢰도를 제공한다는 뜻임. 신뢰도가 0.1인 결과는 무시할 수 있으니, 틀린 답을 맞다고 확신하는 환각과는 다름.
 - 제시한 용도 안에서 비교한다면 오해를 부르는 비교라고 보지는 않음. 품질은 모르겠지만 더 빠르고 저렴하다는 것만으로도 특정 작업에는 바로 매력이 생김. RLCD에 관한 주장이 맞다면, 작업과 무관한 지식이 많은 거대 모델보다 나을 수도 있음.
 - LLM이 생성형 Transformer와 동의어가 되어, 언어를 해석하는 다른 대규모 모델은 별도 이름이 필요해진 걸까? 이것도 디코더가 언어 대신 신뢰도 점수를 출력하는 Transformer일 수 있음. 더 가능성 높은 아키텍처를 안다면 알려주길 바람. 진심으로 궁금함.

 타입은 맞지만 값이 틀릴 수 있다는 건 아마 모든 머신러닝에 해당할 것임. 용어 정의를 두고 논쟁할 수는 있겠지만, 랜덤 포리스트가 LLM과 같은 방식으로 ‘환각을 일으킨다’고 표현하는 건 적절하지 않다고 봄.

- TypeSafe에서 충분히 주목받지 못한 부분은 최신 LLM의 작업 능력을 저렴하게 증류할 수 있다는 점이라고 봄. Jev는 GPT-6-Astra/Fable 5.1 같은 느낌인데, 학습 데이터 상당량은 이전 모델에서 가져온 것 아닐까?
 결국 LLM의 좁지만 매우 흔한 용도를 증류해 최첨단 LLM보다 빠르고 저렴하게 제공하는 구조임. 새 모델이 나오면 RLCD로 가중치를 갱신할 수 있을 것임. 다음으로 최첨단 LLM에서 저렴하게 증류해 효과를 볼 만한 작업은 무엇일까? 직접 이것저것 시험해 봐야겠음.
- 이것으로 LLM용 능동적 기억 생성·검색 시스템을 아주 빠르게 만들 수 있지 않을까? 최근 32k 분량의 컨텍스트와 현재 작업 요약을 넣고, 유용한 내용을 배웠는지 참·거짓으로 판단한 뒤 저장할 분류를 정해 LLM에 저장하도록 알리는 식임.
 검색할 때도 어떤 기억 분류가 유용할지 항목별 확률을 구하고, 다음 단계에서는 분류 태그별로 정렬한 기억의 짧은 설명을 넣을 수 있음. 그중 현재 맥락에서 작업에 도움이 되는 기억이 있는지 다시 예·아니요로 판단하는 구조임.
 조정은 필요하겠지만, 기존 LLM 대화 주변에서 작동하는 훨씬 나은 기억 시스템의 기반이 될 듯함. 범용 입력을 받아 확률을 포함한 지능적 분류를 빠르고 저렴하게 수행한다는 이해가 맞다면 엄청난 기술임.
- 계약 기반 설계와 결합하면 흥미로운 일을 많이 할 수 있겠음. 2025년 초에 이 패턴을 Python으로 옮겨 LLM과 결합했고, 당시 [https://leoveanu.com/2025-03-01-dbc/](https://leoveanu.com/2025-03-01-dbc/)에 글을 썼음. 이후 계약은 SymbolicAI의 핵심 기능이 되었고, 커뮤니티에서도 호응을 얻었음. [https://news.ycombinator.com/item?id=44399234](https://news.ycombinator.com/item?id=44399234).
 아직 거친 구상 단계지만, 검증만 된다면 에이전트 작업을 바꿀 수 있을 것 같음. 제어 흐름에서 매우 빠른 의미 기반 분기를 쓸 수 있기 때문임. 계약을 위해 설계한 데이터 모델을 Jev가 요구하는 형식으로 직접 변환하거나, 사후 조건에서 의미 기반 분기에 Jev를 사용할 수 있을 것임.
 내 이해가 맞는지 더 검토해야겠지만, 늘 하고 싶었으나 방법을 몰랐던 ‘계약 컴파일’과 워크플로 내 계약 연결을 마침내 구현할 수도 있겠음. 시험해 보고 싶어서 대기 명단에 등록함. 

 - nathan@typesafe.ai로 이메일을 보내주면 대기 순서를 앞당길 수 있도록 해보겠음.

- 복잡한 JSON을 포함한 임의의 텍스트와 예·아니요, 객관식, 점수형 질문을 받아 밀리초 단위로 답하고, 비용도 100만 토큰당 0.042달러라니 매우 유망한 구상임. 아쉽게도 발표문에서는 이런 내용이 제대로 설명되지 않지만, 문서는 꽤 잘 되어 있음. [https://docs.typesafe.ai/concepts/how-to-build-with-system-o...](https://docs.typesafe.ai/concepts/how-to-build-with-system-one).
- 문서가 제품을 더 잘 설명하는 듯함. LLM 토큰과의 비교는 다소 혼란스러움. 상태와 Choice, Score, Noul 형태의 질문을 입력받고, 추가 설정을 적용한 뒤 선택 결과·확률·신뢰도 등 알맞은 답을 출력하는 모델로 보임. 상태는 구조화된 텍스트인 것 같은데 멀티모달인지는 모르겠음.
 AI 입문 페이지를 보니 사전 학습된 기반 모델에 RLCD를 적용하는 듯함. [https://docs.typesafe.ai/concepts/system-one](https://docs.typesafe.ai/concepts/system-one). 

 - CEO인데, 그렇게 이해하면 맞음. 출력 토큰은 서로 비교할 수 없기도 해서 LLM 토큰과의 비교가 이해하기 어렵다는 데 동의함.
텍스트나 구조화된 상태를 입력받아 결정을 출력하는 방식임. 여러 텍스트가 들어 있는 JSON도 입력할 수 있고, choice는 match 문에, score는 정렬에, 베르누이의 줄임말인 noul은 if 문에 대응함.
 - 입력뿐 아니라 판단 기준과 지시도 JSON으로 구조화할 수 있음. 모델이 구조를 이해하도록 학습되어 있어서 상당히 강력함. [https://docs.typesafe.ai/primitives/advanced#structured-inst...](https://docs.typesafe.ai/primitives/advanced#structured-instructions).
 멀티모달은 아직 아니고 지금은 JSON만 지원함. 질문에 맞는 답을 출력한다는 이해는 맞음.

- 이론적으로 미완성 텍스트를 넣고 다음에 올 문자가 무엇일지 확률을 물어볼 수도 있지 않을까? 

 - 가능하지만, 텍스트 생성에 최적화된 모델은 아님. 텍스트 생성은 매우 복잡한 작업이며, 길고 일관된 텍스트를 만들려면 모드 드롭핑(mode dropping)이 필요함.
 - 영어의 추상 구문 트리(AST) 를 제공한다면 가능함.
