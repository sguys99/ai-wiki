REA는 AI 에이전트가 소스 코드 없이 다른 앱의 기능을 분석하고 따라 만들게 해주는 오픈소스 도구다. 개발자가 어떤 앱에서 본 기능을 물으면, 에이전트는 REA로 그 앱을 직접 분석해 기능이 어떻게 동작하는지 설명한다. 설명에는 결론마다 근거와 한계가 붙고, 에이전트는 그 분석 결과로 비슷한 기능을 개발자의 프로젝트에 구현한다. 분석 대상은 컴파일된 실행 파일부터 안드로이드 앱과 웹사이트, 기기 펌웨어까지 넓다. 프로젝트의 깃허브 스타는 8만 개를 넘겼다. <박재홍의 실리콘밸리>

![thumbnail](https://static.wikidocs.net/images/blog/33128/featured.png)

## 핵심요약

- 에이전트용 리버스 엔지니어링 도구: REA는 AI 코딩 에이전트가 불러 쓰는 리버스 엔지니어링(소스 코드 없이 완성된 프로그램을 거꾸로 분석하는 일) 도구다. 개발자가 다른 앱에서 본 기능을 물으면 에이전트가 REA로 그 앱을 분석해 동작 원리를 설명한다. 이어서 그 결과로 비슷한 기능을 개발자의 프로젝트에 만들고 테스트한다.
- 결론마다 붙는 근거와 한계: REA는 분석 결과를 돌려줄 때 각 결론을 뒷받침하는 근거와 그 결론의 한계를 함께 담는다. 기계어를 거꾸로 풀어낸 코드는 원본 소스와 같지 않아서, 그것만 보고 내린 결론은 틀릴 수 있다. 근거가 붙어 있으면 개발자가 에이전트의 결론을 그대로 믿지 않고 직접 확인할 수 있다.
- 분석 대상과 필요한 도구: REA는 컴파일된 실행 파일과 데스크톱 앱부터 안드로이드 앱, 웹사이트, 기기 펌웨어까지 한 도구로 분석한다. 다만 실행 파일을 깊이 분석하려면 기계어를 사람이 읽는 코드로 되돌리는 호퍼·기드라·IDA 중 하나가 있어야 한다. 크래시 분석처럼 리눅스 x64에서만 되는 기능도 여럿이다.
- 원본과 대조한 검증: 기계어를 거꾸로 풀어낸 의사 코드가 불완전해도, 원본과 결과를 대조하면 원래 함수를 정확히 복원할 수 있다. 한 공개 사례는 벽돌 깨기 게임 DX볼에서 소리를 좌우 스피커에 얼마나 나눌지(pan) 계산하는 함수를 분석해 C 코드로 다시 짰다. 다시 짠 코드는 3,205가지 경우에서 원본 기계어와 같은 결과를 냈고, 컴파일하면 원본 함수의 63바이트가 그대로 나온다.
- 사용자가 따져야 할 위험: REA를 쓰는 사람은 두 가지를 직접 따져야 한다. 하나는 데이터다. REA는 분석 대상을 업로드하지 않고 사용자 컴퓨터에서 분석하지만, 분석 결과는 에이전트에게 넘어가 모델 제공사의 데이터 정책을 따른다. 다른 하나는 법적 책임으로, 프로젝트는 합법적인 연구용 도구라고 밝히며 필요한 허가를 받고 법을 지킬 책임을 사용자에게 둔다.

## REA는 에이전트에 리버스 엔지니어링 도구를 연결하는 MCP 서버다

REA는 AI 에이전트가 리버스 엔지니어링 도구를 직접 불러 쓰게 해주는 MCP 서버다. 리버스 엔지니어링(역공학)은 완성된 프로그램을 거꾸로 분석해 소스 코드 없이 동작 원리를 알아내는 일이다. MCP는 AI 모델이 외부 도구와 데이터에 접속할 때 쓰는 표준 규약이다. 에이전트는 클로드 코드나 코덱스처럼 도구를 스스로 불러 가며 작업을 끝까지 해내는 AI를 말한다. 이름 REA는 "Reverse Engineer Anything"의 약자로, 무엇이든 리버스 엔지니어링한다는 뜻이다.

REA가 내세우는 쓰임새는 다른 앱에서 본 기능을 이해하고 같은 기능을 내 제품에 만드는 일이다. 프로젝트 소개 문구도 "마음에 드는 기능을 봤다면, 그 기능이 어떻게 동작하는지 바이너리 수준까지 이해하라"이다. 개발자는 에이전트에게 그 기능을 REA로 조사하라고 시킨다. 에이전트는 소스 코드 없이 앱을 검사해 기능이 어떻게 동작하는지 설명하고 근거를 보여준다. 그런 다음 개발자의 프로젝트에 비슷한 기능을 만든다.

분석은 에이전트와 REA가 주고받는 순환으로 진행된다. 에이전트가 MCP로 REA를 불러 대상을 검사하고 관련 코드를 추적하면, REA는 발견한 내용을 근거와 함께 돌려준다. 에이전트는 이 결과를 보고 추가로 질문하거나, 동작을 설명하거나, 구현 코드를 쓰고 테스트한다. 터미널에서 쓰는 CLI(명령줄 도구) 명령도 같은 분석 흐름을 따른다.

REA의 결과 형식을 정하는 원칙은 다음 문장에 담겨 있다.

> Analysis runs locally, and results include the evidence and limitations behind each conclusion. > 분석은 로컬에서 돌고, 결과에는 결론마다 그 결론을 뒷받침하는 근거와 한계가 담긴다.

기계어를 거꾸로 풀어낸 코드는 원본 소스와 같지 않아서, AI가 그 코드만 보고 내린 설명은 그럴듯해도 틀릴 수 있다. 결론마다 근거와 한계가 붙어 있으면 개발자는 에이전트의 설명을 직접 확인하고 어디까지 믿을지 정할 수 있다.

## npx 명령 한 줄로 설치하고 에이전트에게 묻는다

설치는 명령 하나로 끝난다. REA를 쓰려면 Node.js 22.x(22.19 이상), 24.x(24.11 이상), 26 이상 중 하나와 npm이 있어야 한다. 준비가 됐으면 다음 명령을 실행한다.

```
npx rea-agents setup

 코드 복사
```

명령을 실행한 뒤 연결할 에이전트를 고르고, 설정 변경 내용을 확인해 승인한다. 설치하면 REA의 MCP 서버가 에이전트에 등록되고, 분석 절차를 담은 작업 지침도 함께 깔린다. 기존 설정은 백업해 두며, 설치가 끝나면 에이전트를 다시 시작해야 한다. 설치 도구가 바로 지원하는 에이전트는 클로드 코드·코덱스·커서·제미나이 CLI·그록 빌드 등이다. 로컬 MCP 서버를 지원하는 에이전트라면 어느 것이든 MCP 서버를 직접 등록해 쓸 수 있다.

skills.sh에서 REA 스킬만 따로 설치할 수도 있다. 스킬은 에이전트에게 조사 방법을 알려주는 지침 파일이다. 하지만 스킬만 설치하면 MCP 서버는 등록되지 않으므로, 원문은 npx rea-agents setup으로 둘을 함께 설치하라고 권한다.

실행 파일을 깊이 분석하려면 디스어셈블러·디컴파일러가 하나 필요하다. 이 도구들은 기계어를 어셈블리어나 C 비슷한 코드로 되돌린다. REA는 호퍼(Hopper), 기드라(Ghidra), IDA 중 하나를 쓴다. REA는 이 도구들을 분석 엔진(provider)이라고 부른다. 기드라와 IDA는 이미 설치된 것을 쓰고, 호퍼는 사용자가 승인하면 설치 과정에서 함께 깔아준다. REA는 호퍼가 필요할 때 직접 실행하므로 미리 띄워둘 필요가 없다. 맥OS에서는 처음 실행할 때 데모 모드로 쓸지, 라이선스를 활성화할지 묻는 창이 뜰 수 있다. 자바스크립트 정적 분석과 .NET 분석은 분석 엔진 없이 돈다.

설치가 끝나면 에이전트에게 평소처럼 말로 시킨다. 원문이 든 예시는 다음과 같다.

```
Understand how search works in the Notes app, show me the evidence, and build a
similar feature for my project.

 코드 복사
```

Notes 앱의 검색이 어떻게 동작하는지 파악하고, 근거를 보여주고, 내 프로젝트에 비슷한 기능을 만들어 달라는 요청이다. Notes 자리에는 분석할 앱을, 검색 자리에는 알고 싶은 기능을 넣으면 된다.

에이전트 없이 터미널에서 직접 분석할 수도 있다. 다음 명령은 자바스크립트·일렉트론(Electron, 웹 기술로 데스크톱 앱을 만드는 프레임워크) 앱을 분석한다. 대상은 압축을 푼 앱 디렉터리나 ASAR 파일이다.

```
npx -y rea-agents@latest analyze-javascript-application /absolute/path/to/app --json

 코드 복사
```

ASAR는 일렉트론 앱의 소스 파일을 하나로 묶은 아카이브 파일이다. 분석 결과에는 모듈과 import 관계가 근거와 함께 담긴다. 화면을 그리는 프로세스와 운영체제에 접근하는 프로세스가 어디서 나뉘는지도 보여준다. 경로는 분석할 대상으로 바꾸고, 윈도우라면 "D:/apps/example"처럼 쓴다.

REA를 자주 쓴다면 rea 명령을 전역으로 설치한다.

```
npm install --global rea-agents
rea --
help

 코드 복사
```

네이티브 분석 명령을 쓰려면 먼저 쓸 분석 엔진을 설정해야 한다. 분석 엔진 선택, 분석 스냅숏, 스크립트 작성 방법은 저장소의 CLI 가이드에 있다.

REA는 빠르게 바뀌고 새 릴리스마다 버그 수정이 자주 들어간다. 그래서 원문은 늘 최신 버전을 유지하라고 권한다. npm이나 Bun으로 전역 설치했다면 다음 명령으로 업데이트한다.

```
rea update

 코드 복사
```

Bun 전역 설치는 Bun 1.2.17 이상에서만 이 명령으로 업데이트된다. 그보다 오래된 Bun이라면 Bun부터 직접 올린다. 업데이트가 끝나면 화면에 출력되는 설정 명령을 실행해 에이전트 등록과 스킬도 새로 고친다. npx로 쓰는 경우에는 다음 명령으로 에이전트 설정을 갱신하고, 변경 사항을 확인한 뒤 에이전트를 다시 시작한다.

```
npx rea-agents@latest setup

 코드 복사
```

한 번만 쓰는 CLI 명령은 npx rea-agents@latest 뒤에 명령을 붙여 실행하고, Bun이라면 bunx rea-agents@latest를 쓴다. 버그를 만나면 먼저 업데이트하고 같은 작업을 다시 해본다. 그래도 문제가 남으면 REA 버전과 대상 종류, 재현 절차, 오류 출력을 담아 이슈를 연다.

## 분석 대상: 컴파일된 실행 파일부터 펌웨어까지

REA는 대상 종류마다 다른 분석 도구를 MCP 서버 하나로 묶었다. 가장 깊은 분석은 네이티브 바이너리에서 이뤄진다. 네이티브 바이너리는 CPU가 바로 실행하는 기계어로 컴파일된 실행 파일이다. REA는 이런 파일에서 의사 코드(pseudocode)와 어셈블리, 문자열, 함수 호출 관계를 뽑아준다. 의사 코드는 디컴파일러가 기계어를 C 비슷한 모양으로 되돌린 코드이며, 원본 소스와 같지 않다.

원문이 정리한 분석 대상은 다음과 같다.

대상REA가 돌려주는 것필요한 것

네이티브 바이너리의사 코드, 어셈블리, 문자열, 심볼, 호출과 참조호퍼·기드라·IDA 중 하나

오프라인 ELF 구조섹션, 세그먼트, 원래 심볼과 재배치 정보, 정적 보안 완화 기법 후보리눅스 x64, 사용자가 준비한 pwntools

EVM 바이트코드함수 디스패치 셀렉터, 바이트 오프셋, 추정한 인자, 상태 변경 여부리눅스 x64, 로컬 raw/hex 파일

기록된 리눅스 크래시코어 파일의 노트 원문(raw notes), 기록된 모든 스레드의 레지스터와 시그널, 메모리 매핑 후보(선택)리눅스 x64, 사용자가 준비한 pwntools, GDB/pwndbg(선택)

자바스크립트/일렉트론모듈, import, 소스맵, 라우트, IPC, 네이티브 애드온 관계Node.js, npm

웹사이트페이지 구조, 스크립트, 네트워크 관찰 결과, 요청한 스크린샷크롬 계열 브라우저

저장된 네트워크 캡처요청, 응답, 노출된 페이로드, 소스 위치HAR 파일, mitmproxy 캡처는 리눅스의 mitmdump

.NET 어셈블리메타데이터, CIL 명령어, 선언된 네이티브 의존성, 빌드 간 비교없음(정적 분석만)

안드로이드 APK매니페스트 선언, 클래스, 디컴파일한 메서드, 참조헤드리스 JADX, 전체 JDK(리눅스·맥OS·윈도우 x64)

안드로이드 기기기기, 패키지, 프로세스, 로그, 덤프, 화면 캡처, APK·파일 전송사용자가 준비한 adb(에뮬레이터나 실기기)

JEB 프로젝트엔진 기반 프로젝트 단위, 산출물 다이제스트, 타입·메서드 의사 코드사용자가 띄운 MCP 지원 JEB 클라이언트, REA_JEB_MCP_URL로 지정

안드로이드 리소스디코딩한 매니페스트, 문자열 테이블, 로캘, 버전 정보사용자가 준비한 Apktool

펌웨어영역, 추출 결과, 네이티브 분석으로 넘길 대상리눅스의 Binwalk·Unblob

패키지와 리소스파일 목록, 다이제스트, plist, 애플 번들 구조, 추출한 리소스따로 적힌 도구 없음

프로세스 동작터미널 출력, 입력 상호작용, 종료와 파일 시스템 관찰, 실행 간 비교네이티브 PTY가 있는 리눅스·맥OS

표에서 ELF 구조·EVM 바이트코드·리눅스 크래시 분석은 보안 연구자를 위한 기능이다. ELF는 리눅스 실행 파일 형식이고, EVM(이더리움 가상 머신) 바이트코드는 이더리움 스마트 컨트랙트가 실제로 실행되는 코드다. pwntools는 보안 연구와 해킹 대회에서 널리 쓰는 파이썬 도구 모음이다. REA는 실행 파일에 걸린 보안 완화 기법(mitigation)의 후보를 찾고, 크래시 기록도 분석한다. 보안 완화 기법은 공격을 어렵게 만드는 보호 장치다. 원문은 일반 개발자를 앞세우지만, 이 기능들은 보안 분석 쪽에 가깝다.

안드로이드 쪽은 네 갈래다. 앱 설치 파일인 APK는 JADX로 디컴파일하고, 연결한 기기는 adb로 다루며, 앱 리소스는 Apktool로 디코딩한다. 상용 분석 도구인 JEB를 쓰고 있다면 JEB 프로젝트도 불러온다.

분석은 실행 여부에 따라 두 방식으로 나뉜다. 정적 분석(static analysis)은 파일만 읽고 앱을 실행하지 않는다. 자바스크립트와 .NET 분석이 여기에 해당한다. 반면 런타임 캡처는 대상을 실제로 실행하거나 조작하며, 사용자 계정의 권한으로 돈다. 그래서 런타임 기능마다 가이드에 그 기능이 시스템에 미치는 영향이 따로 적혀 있다.

네이티브 분석에서 지원하는 파일 형식과 운영체제는 분석 엔진마다 다르다. 윈도우에서 기드라를 분석 엔진으로 쓰는 것은 아직 실험 단계다. 기드라는 16비트 DOS 프로그램도 분석한다. 큰 바이너리를 기드라로 열다가 시간이 부족하면 REA_GHIDRA_STARTUP_TIMEOUT_MS 환경 변수로 시작 제한 시간을 늘린다. 최신 npm 릴리스 이후 추가된 기능은 저장소의 릴리스 현황 문서에서 확인한다.

MCP가 2024년 말 공개된 뒤, 분석 도구 하나를 에이전트에 붙이는 MCP 서버가 여럿 나왔다. 기드라용 GhidraMCP와 IDA용 ida-pro-mcp가 그 예다. REA는 도구 하나가 아니라 분석 대상을 기준으로 여러 도구를 묶었다는 점이 이들과 다르다. 에이전트는 대상이 무엇이든 같은 MCP 서버를 부르면 된다. 대신 필요한 도구와 운영체제가 대상마다 갈린다. ELF·EVM·크래시 분석은 리눅스 x64에서만, 펌웨어 추출은 리눅스에서만 돌고, pwntools·adb·Apktool·JEB처럼 사용자가 직접 갖춰야 하는 도구도 많다.

## 사례 세 가지: 옛 게임 함수 복원과 노션 클립보드 추적

원문이 소개하는 사례 셋 중 둘은 옛 게임의 계산 함수를 복원해 원본과 대조했고, 하나는 노션의 클립보드 처리 경로를 추적했다.

첫 번째는 벽돌 깨기 게임 DX볼(DX-Ball)이다. 분석은 소리를 내는 함수 호출에서 시작해, 위치 값을 좌우 스피커 배분 값(pan)으로 바꾸는 보조 함수까지 따라갔다. 그 함수의 기계어 명령어를 살핀 뒤, 불완전하게 나온 의사 코드를 C 코드로 다시 썼다. 다시 쓴 C 코드는 원본 x86 코드와 결과를 비교한 3,205개 경우를 모두 통과했다. 이 코드를 컴파일하면 원본 함수를 이루는 63바이트가 하나도 다르지 않게 나온다. 동작만 같은 것이 아니라 기계어까지 원본과 같다는 뜻이다. 사례 글과 함께 복원 코드 저장소도 공개돼 있다.

두 번째는 노션(Notion)의 클립보드 기능이다. 노션의 데스크톱 앱은 일렉트론으로 만들어졌다. 일렉트론 앱은 화면을 그리는 렌더러 프로세스와 운영체제 기능에 접근하는 메인 프로세스로 나뉜다. 두 프로세스 사이에는 프리로드 스크립트가 다리를 놓고, 두 프로세스는 IPC(프로세스 간 통신)로 메시지를 주고받는다.

사례에서는 렌더러가 쓰는 클립보드 API를 먼저 찾았다. 그다음 그 호출을 프리로드와 IPC를 거쳐 메인 프로세스까지 따라갔다. 마지막으로 서식이 담긴 클립보드 데이터의 형식을 살폈다.

세 번째는 일본 NEC의 옛 PC인 PC-98용 슈팅 게임 TH04다. TH04는 동방 프로젝트의 네 번째 작품인 동방환상향을 가리킨다. 분석은 원본 게임의 16비트 명령어를 살펴, 탄환을 고리 모양으로 뿌릴 때 쓰는 각도 계산 두 가지를 복원했다. 하나는 정해진 각도로 뿌리는 계산이고, 다른 하나는 플레이어를 겨냥하는 계산이다. 복원한 C++ 코드는 당시 컴파일러가 실제로 내놓은 출력과 비교해 검증했다. 이 사례도 복원 코드 저장소가 공개돼 있다.

두 게임 사례는 모두 복원 결과를 원본과 대조해 검증했다. 의사 코드만으로는 정확한 복원을 보장할 수 없기 때문이다. 원문은 REA로 흥미로운 대상을 분석했다면 대상과 질문, REA가 도운 방식, 발견한 내용을 담아 이슈나 풀 리퀘스트로 공유해 달라고 요청한다.

## 분석은 로컬에서, 법적 책임은 사용자에게

REA는 대상 앱을 업로드하지 않고 사용자 컴퓨터에서 분석한다. 다만 분석 결과는 에이전트에게 전달되고, 에이전트를 돌리는 모델 제공사는 자체 데이터 정책을 따른다. 사내 기밀 바이너리를 분석한다면 결과에 담긴 코드 조각과 문자열이 모델 제공사로 넘어간다는 점을 따져봐야 한다.

프로젝트는 REA가 합법적인 리버스 엔지니어링 연구와 분석, 재구성을 위한 도구라고 밝힌다. 필요한 허가를 받고 관련 법을 지키는 것은 사용자의 책임이다. 프로젝트는 불법적이거나 허가받지 않은 사용을 지지하지 않는다고 명시한다.

프로젝트는 암호화폐나 토큰을 발행하거나 보증한 적이 없다고 따로 밝힌다. REA 이름을 쓰는 토큰은 프로젝트와 관계가 없다. 이런 고지가 따로 있다는 것은 REA 이름을 내건 토큰이 실제로 돌고 있다는 뜻이다. REA는 깃허브 스타 8만 개를 넘겼고, 인기 오픈소스에 사칭 토큰이 붙는 일은 흔하다.

라이선스는 MIT다. MIT 라이선스는 저작권 고지만 남기면 상업적 사용과 수정을 모두 허용하는 오픈소스 라이선스다. 보안 취약점은 저장소의 SECURITY.md 절차로 신고하고, 개발 환경과 기여 방법은 CONTRIBUTING.md에 있다.

## 실리콘밸리 영어

down to the binary level (바이너리 수준까지 샅샅이)

- 원문: "See a feature you like. Understand how it works, down to the binary level."
- 번역: 마음에 드는 기능을 봤다면, 그 기능이 어떻게 동작하는지 바이너리 수준까지 이해하라.
- 설명: down to the ~ level은 "가장 밑바닥 단위까지 빠짐없이"라는 뜻이다. down to the last detail(마지막 세부까지), down to the millisecond(밀리초 단위까지)처럼 down to 뒤에 가장 작은 단위를 붙여 철저함을 강조할 때 쓴다.

worked example (풀이 과정을 보여주는 예제)

- 원문: "Your agent uses these findings to write and test an implementation; the showcases give worked examples."
- 번역: 에이전트는 이 분석 결과로 구현 코드를 쓰고 테스트한다. 쇼케이스에 처음부터 끝까지 풀어 보인 예시가 있다.
- 설명: worked example은 답만 보여주는 예시가 아니라 풀이 과정을 처음부터 끝까지 보여주는 예제다. 교재의 "예제 풀이"에서 온 말로, 기술 문서에서 따라 하며 배우는 예시를 가리킬 때 자주 나온다. 같은 원문의 worked guides도 같은 쓰임이다.

not affiliated with (~와 공식 관계가 없다)

- 원문: "Tokens using the REA name are not affiliated with the project."
- 번역: REA 이름을 쓰는 토큰은 이 프로젝트와 관계가 없다.
- 설명: affiliated with는 조직끼리 공식적으로 연결돼 있다는 뜻이고, 부정형은 면책 고지에서 "우리와 상관없다"를 격식 있게 말할 때 쓰는 단골 표현이다. 짝으로 endorsed by(보증을 받은)도 자주 나오며, 원문도 바로 앞 문장에서 "We have not issued or endorsed any cryptocurrency"라고 썼다.

## 핵심통찰

REA는 전문 도구를 손에 익힌 사람의 일이던 리버스 엔지니어링을 에이전트에게 던지는 질문 한 줄로 바꾼다. 진입 장벽이 낮아진 만큼, 무엇을 분석하고 그 결과로 무엇을 만들어도 되는지에 대한 판단은 개발자 개인의 몫이 된다. 남의 앱을 분석해 비슷한 기능을 만드는 일은 소프트웨어 사용권 계약(EULA)의 역공학 금지 조항과 부딪칠 수 있다. 업계는 이 위험을 줄이려고 분석하는 사람과 구현하는 사람을 나누는 클린룸 설계(clean-room design)를 써 왔는데, 에이전트 하나가 분석과 구현을 모두 하면 이 구분이 사라진다. 그래서 REA를 실무에 쓰기 전에는 대상 앱의 사용권 계약과, 분석 결과가 모델 제공사로 넘어가도 되는지에 대한 회사 정책부터 확인해야 한다.
